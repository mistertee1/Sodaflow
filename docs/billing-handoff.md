# تسليم عمل SudaFlow — 2026-10-05

## حالة المصدر والنشر

دُمج نظام الاشتراكات من `codex/central-billing-isolated` إلى `main` عبر PR رقم 12. كانت نتيجة الدمج تحتوي مدخلي تشغيل مختلفين في `netlify/functions/api.ts` ومراقب revision مختصراً فقد تعافي الانقطاع. أصبح ملف API يحتوي مدخل Netlify حديثاً واحداً؛ استُعيد تعافي المراقبة في `src/services/revisionWatch.ts` مع الحفاظ على تعديلات المحاسبة التي نشرها الإيجنت الآخر.

الحفظ المالي في المصدر الحالي يمر عبر API ويطبق حدود الاشتراك داخل معاملات Firestore. مراقبة revision تستخدم Web SDK مع `experimentalForceLongPolling: true` مثل مرجع `Hesabak-main.zip`، وقراءات SDK مؤكدة من الخادم بعد فشل المستمع، ثم API عند رفض تلك القراءة بالقواعد. إعادة المطابقة كل 30 ثانية وعند عودة الاتصال موجودة في AppContext أيضاً. الكاش للعرض فقط ولا يثبت نجاح الحفظ.

علامة النسخة الجديدة هي `2026-10-05-central-sync-recovery`، في HTML وفي نتيجة `/api/health`. **وجود المصدر في GitHub لا يثبت نشره على Netlify.** أثناء هذه الجولة ظل API الحي يعرض `3.0.3-netlify` ولم يظهر مدخل الإصلاح الجديد. لم تُؤكد مزامنة حساب العميل أو حفظ معاملة من جلسة دخول فعلية.

## سبب العطل المؤكد

الطلب التشخيصي غير الكتابي إلى `firestore.googleapis.com` للمشروع `sodaflow` وقاعدة `(default)` أعاد HTTP 403 و`google.rpc.ErrorInfo.reason = SERVICE_DISABLED` للخدمة `firestore.googleapis.com`. رقم المشروع `715757175054` مطابق لإعداد Firebase ولبيانات Firebase Auth العامة؛ لا تغير المشروع إلى مشروع المرجع القديم `hesabak-b9658`.

إذن Cloud Firestore API معطّلة. تغيير Firestore Security Rules وحده لا يعالج ذلك. الخادم الحي يملك اعتماد Firebase صالحاً، لكن مصنّف الخطأ القديم يعرض `firestore_access_denied` لجميع أخطاء gRPC 7. المصنّف الجديد يميز `firestore_api_disabled` دون كشف تفاصيل المفاتيح أو طلبات المستخدمين. بعد تفعيل الخدمة أعد فحص الجاهزية؛ قد تظهر حينها مشكلة مختلفة في القاعدة أو IAM ويجب معالجة السبب المحدد.

Storage يعيد `storage_bucket_missing`؛ مشكلة رفع الصور مستقلة عن قراءة وحفظ الفواتير. لا تفتح القاعدة للعامة، ولا تنشئ شركة بديلة، ولا ترفع بيانات محلية فوق سجلات الإنتاج لمعالجة انقطاع الاتصال.

## حدود الوصول والمحاولة المؤقتة

حساب تكامل Netlify المتاح لا يعرض مشروع `sodaflow`. لوحة المشروع في المتصفح تطلب تسجيل الدخول. رفضت المراجعة التلقائية طلب الدخول الآمن الجديد لأن المستخدم رفض طلباً سابقاً ولم يُعد التصريح بالدخول صراحةً. لا تعاود تسجيل الدخول أو تتجاوز هذا الرفض عبر استخراج مفاتيح أو جلسات دون تصريح جديد.

أضيفت مؤقتاً دالة صيانة بمشروع ثابت ورمز عشوائي مجزأ ووقت انتهاء، لمحاولة تفعيل Firestore باستعمال اعتماد التشغيل داخل Netlify دون كشفه أو منح IAM. الموقع أعاد 404 HTML بدلاً من تشغيلها، لذلك لم تنفذ أي إجراء Google Cloud. حُذفت الدالة من `main` في commit `c3bbb756ab1f28cfa1d0158296f6b4e540bf4016` وحُذف الرمز المحلي. لا توجد دالة صيانة أو مفتاح جديد في المصدر الحالي.

لم يُغير IAM، ولم تُشغّل migration أو bootstrap أو deploy Rules في هذه الجولة. لا توجد صلاحية Super Admin مُنحت تلقائياً. هوية UID الإدارة العليا لم تُحدد بعد.

## ما يلزم لإكمال التشغيل

1. استعادة وصول إدارة المشروع وتفعيل Cloud Firestore API في المشروع الصحيح. تحقق أن قراءة Firestore الخادمية تنجح؛ جاهزية Storage ليست شرطاً لمزامنة الفواتير.
2. راجع [خطوات التفعيل](operations.md)، وخذ النسخة الاحتياطية ثم معاينة الترحيل قبل تطبيقه. يحفظ الترحيل المالك والسجلات وحصة الاستخدام التاريخية، ولا يبدل العقود المدفوعة غير الموثقة.
3. عيّن UID إدارة محدداً ببريد مؤكد عبر إجراء bootstrap؛ لا تمنح Owner الشركة إدارة المنصة. انشر API والقواعد والفهارس في نافذة متناسقة بعد جاهزية الخدمة.
4. تحقق من علامتي النشر والجاهزية ثم من المزامنة داخل جلسة العميل؛ لا تعتبر تحميل واجهة الضيف أو الكاش دليلاً على نجاح الاتصال السحابي.

راجع أحدث `main` قبل أي كتابة، واستعمل تحديثاً عادياً بلا force push. TypeScript وبناء الإنتاج فحوص مصدر فقط؛ لم تُشغّل الاختبارات الآلية وفق طلب المستخدم. الفروع والمخازن لها حقول حدود تمهيدية؛ بوابة الدفع وعمليات إدارة مواقع كاملة تحتاج تنفيذاً لاحقاً.
