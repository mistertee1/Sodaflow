# تقرير C2.2b.2.2 — التسجيل والتسوية الافتتاحية الذرية

تاريخ التقرير: 2026-10-08 UTC. الفرع `codex/accounting-v2-c2-opening-transactions` تابع لـ[PR28](https://github.com/mistertee1/Sodaflow/pull/28). الربط المالي والتقارير والاستعادة في الأساس مؤكدة باختبارات CI؛ هذا التغيير يضيف أوامر الخادم. **مساعد الواجهة C2.2b.3 ورأس المال/المسحوبات C2.3 ما زالا قادمين، ولا تُعد المرحلة C أو الجاهزية التجارية مكتملة.**

## ما نُفّذ

- أمر `opening.commit` عبر مسار العمليات الحالي، بصلاحية `opening:write` للمالك الحقيقي فقط. يتطلب auth_time من رمز Firebase الذي تحقّق منه الخادم خلال خمس دقائق؛ قيم المالك أو الزمن أو المؤسسة أو القيد في body لا تمنح صلاحية.
- يقبل فقط input وterms وexpected_preview_hash. يعيد قراءة كل النشاط المالي الفعلي، ويحسب أساس المعاينة من المصدر والفترة والحد القديم والدقة. التغيير أو النشاط المخفي أو فرق OpeningEquity غير المراجع يرفض الطلب. البصمة فحص حداثة، وليست توقيع اعتماد.
- يكتب الدفعة وlots المستقلة والقيد وحركة WAC والأرصدة الحالية وعدّادات المصادر والتدقيق ونتيجة idempotency داخل المعاملة نفسها. لا ينشئ فواتير وهمية ولا يستبدل تاريخاً مالياً. تبقى مصادر الافتتاح غير قابلة للتعديل عند التسوية.
- أمر `openingSettlement.create` بصلاحية `opening:settle` للمالك والمحاسب النشط. يقبل lot_id والتسلسل الحالي والعملة/المبلغ والحساب المالي وسعر الصرف والتاريخ والسبب والمرجع؛ يولد الخادم معرف الحدث والقيد. يعيد إثبات سلسلة المصدر كلها، ويتحقق من cache الحالي قبل توزيع القيمة التاريخية. الدفعة الأخيرة تغلق الدفترين، وفروق الصرف في 4200/5500 منفصلة.
- سداد AP يفحص رصيد النقدية في **SDG وUSD معاً** في تاريخ الدفع وكل إقفال يومي لاحق متأثر، لمنع السداد القديم الذي يستهلك أموالاً صُرفت لاحقاً. العملة وربط الحساب النشط وفهرسه يجب أن يتطابقا. AR يُقبض في الحساب نفسه.
- كل أمر يعيد فحص العضوية والتعليق والاشتراك وميزات الكتالوج الحالية وV2 وقواعد الخادم والفترة المفتوحة/المعاد فتحها والحد القديم قبل النتيجة المحفوظة. المعاينة تبين قابلية عرض اعتماد الافتتاح للمالك إذا اكتملت مراجعة الفرق، لكن التنفيذ يحتاج التحقق الحديث والفحوص الحالية.
- إعادة الطلب نفسه لا تكرر القيد أو التدقيق. بعد تغيير لاحق في المؤسسة، يرفض الرد القديم بـ409 ويطلب تحديث الحالة، حتى لا يعيد تطبيق cache قديم في الواجهة. idempotency مختلف المحتوى أو الشخص يرفض؛ مصادر الطلب المحفوظ تُفحص مجدداً.
- معاملات Firestore تقرأ الحالة السابقة رغم buffered writes؛ لذلك نبني overlay مستقلاً ونطابق AR/AP/المخزون/النقدية ومصادر الافتتاح والدليل وإثبات الفترات والمطابقات قبل إرسال الكتابات. تُفحص المسارات الفعلية أيضاً، كي لا يُخفي حقل id مختلف تصادماً في مسار حركة/قيد أو مصدر. فشل الحفظ يرجع العملية كاملة.
- التدقيق يسجل السبب والمالك والتحقق الموثوق والبصمة/الدفعة أو تسلسل lot والقيمة قبل/بعد والتسوية والنقدية وفروق الصرف، بجانب old/new caches. لا يكرر snapshot الكامل الكبير داخل audit.

## التحقق

نجح محلياً `npm run check`: **240 اختبار وحدة/API**، فحص الأنواع والفحص الصارم والبناء. أضيفت 13 حالة تتضمن:

- افتتاح نقدية بالعملتين وAR/AP قديم الاستحقاق ومخزون ورأس مال، TB/Balance Sheet ومطابقة دون فروقات، ثم retry واحد دون تكرار التدقيق.
- المالك الفعلي مقابل Accountant/Admin/Viewer/Sales/Cashier وOwner مزيف وSuper Admin خارج عضوية الشركة؛ تحقق قديم أو مفقود أو من المستقبل؛ تعليق وميزات وفترات وحد قديم قبل cache.
- معاينة قديمة وحقول محمية ونشاط مالي مخفي وOpeningEquity بلا سبب، وسباق افتتاح/دفع زائد وإقفال، وتصادم مسار يخفيه مستند تهيئة صفري.
- تسويات جزئية ونهائية وفروق صرف، وعجز نقدي في أي دفتر عند الدفع أو في يوم لاحق.
- متجر buffered يشبه قراءة Firestore، وفشل persistence بعد إعداد الكتابات دون انحراف المصادر/الأرصدة/العدادات/audit.
- HTTP يستخدم auth_time الموثق فقط؛ وضع SDG فقط لا يختلق USD؛ والفاتورة والشراء والقبض والإشعارات الدائنة والردود والمردودات بعد الافتتاح تحافظ على مجموعات الذمم الافتتاحية وWAC.

أضيفت **3 اختبارات Firestore** داخل `demo-sudaflow` وlocalhost:8091 فقط: سباقات افتتاح وسداد حقيقية مع الإقفال التاريخي للدفترين ومنع SDK، العجز النقدي اللاحق دون أي كتابة جزئية أو rate/audit drift، وسباق الإغلاق النهائي والافتتاح. تنتظر CI؛ لا يُدّعى نجاح emulator أو المتصفح محلياً على Java17. مجموعة الواجهة الحالية تشمل عرض وتصدير مصادر الافتتاح على الهاتف؛ **ليست اختبار مساعد افتتاح أو حوار تسوية جديد**.

أساس PR28 مؤكد على `5bf46badcc5510c6b72c7e1e6a5613bb328bbf03`: [CI37745317689](https://github.com/mistertee1/Sodaflow/actions/runs/37745317689)، 227 وحدة/API و28 Firestore و45 واجهة وصفر ثغرات إنتاج. نتائج هذا الفرع تُثبت بعد اكتمال CI الخاص به.

## الحدود والتالي

حدود البداية 97 مصدراً/100 سطر، دفعة واحدة، 200 تسوية لكل lot، و1200 مستند لكل مجموعة. حجم إثبات البداية/المعاينة لا يتجاوز 650KB؛ audit لا يتجاوز 650KB ونتيجة idempotency لا تتجاوز 900KB، وعدد الكتابات الفعلي يبقى ضمن 450 مع رفض ذري قبل الحفظ. الاستعادة تحتفظ بحدودها الأصغر. الشركات ذات التاريخ الكبير تحتاج مساراً مضبوطاً؛ لا يعالج الأمر ترحيلاً إنتاجياً.

فحوص النسخة والمصدر تثبت الاتساق الداخلي، ولا توقع أصالة نسخة خارجية كاملة. لم يُختبر حساب OAuth/كلمة مرور إنتاجي في هذه المرحلة. لم يتغير Super Admin أو إعدادات مزامنة Firebase أو قواعده، ولم يحدث دمج أو كتابة main أو نشر أو تغيير بيانات إنتاج.

التالي: تأكيد CI ثم C2.2b.3 مساعد بدء الأرصدة وتسوياتها مع معاينة/reauth/منع تكرار الإرسال، ثم C2.3 رأس المال والمسحوبات، وC3–C6 وD/E وExcel1–4 ومتطلبات القبول النهائي.

## تصحيح اختبار CI الأول

تشغيل CI37747896186 أكد 240 وحدة/API وصفر ثغرات إنتاج، واجتاز 30 من 31 اختبار Firestore. فشل اختبار العجز النقدي عند تهيئة حالته الثانية برسالة «الفترة موجودة»: مساعد الاختبار مرر initial=true لنفس المالك، فيعيد مسار التسجيل org-uid نفسه رغم operationId المختلف. عُزلت كل حالة باستخدام إنشاء مؤسسة إضافية بمعرف العملية؛ لم يتغير منطق التسجيل أو حماية الفترات أو أوامر المحاسبة. ينتظر التصحيح CI جديداً، وتبقى الواجهة غير مؤكدة لهذا الالتزام حتى نجاحه.
