# Excel4.1e.2c.2b.1 — عقد ربط الاعتماد بالمعاينة (قيد CI)

2026-10-23 — PR124 تابع لـPR123، المستخدم وحده يراجع ويدمج.

## المنفذ

تعيد المعاينة review_sha256 من صيغة canonical تتضمن إصدار العقد والمؤسسة وuid للمراجع ومعرف العملية ومدخلات الاعتماد وكل نتائج get/list/find التي استخدمها تحقق الاعتماد الكامل، بما فيها الأدلة المحفوظة والمصادر والفترات والعدادات والصلاحيات. تُرتب قوائم القراءات ترتيباً ثابتاً، وتُستبعد ساعة إنشاء المعاينة حتى لا تتغير البصمة لمجرد تقدم الساعة؛ تبقى التحققات الزمنية الحية نافذة.

عند إرسال expected_review_sha256 مع historicalImport.commit، تعاد معاينة كاملة دون كتابة داخل نفس transaction الحالية، وتُقارن البصمة قبل أول كتابة حتى rate-limit. اختلاف الحالة أو البصمة أو المدخلات يفشل مغلقاً. لا توجد نافذة بين فحص المعاينة والالتزام لأنهما يشتركان في معاملة الخادم. إعادة طلب مطابق بعد الحفظ تستخدم إيصال idempotency المتحقق منه؛ البصمة جزء من fingerprint الطلب، فلا يمكن تبديلها في المحاولة المكررة.

## التحقق

نجحت 18 اختبارات historical commit محلياً، بما فيها نجاح journal/sales/purchase بالبصمة، ثباتها بعد تقدم الساعة، عدم تكرار الحفظ عند retry، ورفض تغير revision أو digest مزور أو سبب/مراجع/operationId مختلف دون تغير التخزين. إعادة المعاينة بعد تغير الحالة تولد بصمة جديدة وتسمح بالطلب المطابق. نجح npm run check: TypeScript/core و84 Excel/import و382 وحدة/API والبناء، صفر فشل. الاختبارات ببيانات MemoryStore معزولة وRules verifier محاكاة؛ ليست قبول Firebase حي. CI/Firestore/Playwright لهذا الرأس مطلوب.

## الحدود والتالي

الربط اختياري عند وجود expected_review_sha256 للتوافق مع عقود الاعتماد السابقة؛ لا ادعاء أن كل عميل قديم ملزم بهذه المعاينة بعد. لا زر اعتماد بالواجهة في هذا الجزء. يلزم بعد قبول CI ربط الموافقة الصريحة بالواجهة بمعرف العملية والبصمة وإعادة المحاولة وعزل المؤسسة/تغير الحالة، وتحديد إلزام العقد المراجع قبل قبول الترحيل كاملاً. تبقى الوثيقة وExcel4 والجاهزية التجارية غير مكتملة، وقبول Firebase الحي ومراحل legacy migration/auditor/scheduled exports مستقلة. حُفظت فروع العملات وSuper Admin/المزامنة؛ لا main write أو دمج أو نشر أو بيانات/قواعد إنتاج.
