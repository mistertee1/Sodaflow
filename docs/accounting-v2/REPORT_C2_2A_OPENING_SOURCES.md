# تقرير C2.2a — إثبات مصادر الأرصدة الافتتاحية وتسوياتها

تاريخ التقرير: 2026-10-08 UTC. الفرع `codex/accounting-v2-c2-opening-source-proof` تابع لفرع C2.1 في PR25. هذه مرحلة عقود خالصة للتحقق والحساب؛ **لا يوجد فيها API أو واجهة أو ترحيل فعلي للأرصدة**. مرحلة C2.2b ستربط العقود بالمعاملة والواجهة والمطابقة والاستعادة.

## ما تم

- اشتقاق أهلية مؤسسة V2 الجديدة من المستندات المالية الفعلية في جميع المجموعات المطلوبة. غياب مجموعة ليس دليلاً على خلوها، وcounters لا تمنح أهلية. أي قيد أو نشاط مالي يمنع البدء فوق التاريخ القائم. تهيئة مخزون صفرية موثقة فقط لا تحمل نشاطاً مالياً؛ الكمية أو القيمة أو رابط القيد أو الحركة غير المعروفة تمنع الاستثناء.
- بناء إثبات افتتاح محفوظ مع مصدر وقيد مستقل، وأطراف AR/AP مستقلة تحمل العملة والقيمتين الدفتريتين والتاريخ والاستحقاق والمرجع الأصلي. يجوز الاستحقاق قبل تاريخ البدء لعرض دين قديم متأخر؛ لا يُستنتج من تاريخ إنشاء المؤسسة، ولا تُختلق فاتورة أو إيرادات. يتحول المخزون إلى كمية وقيم ومتوسط تكلفة WAC مثبتة.
- حفظ أساس الافتتاح بالحقول اللازمة فقط، دون نسخ هواتف الأطراف أو ملاحظاتهم الخاصة. المراجعة التاريخية تستخدم هذا الأساس الصفري الأصلي، لا القيم الحالية التي تتغير بعد النشاط. تغيير حالة الطرف أو كمية المخزون الحالية لا يمحو أصل الإثبات؛ فقد الطرف أو تغيير ربط حساب النقدية يوقف التحقق.
- عقد تسويات جزئية ونهائية يحفظ القيمة الدفترية الأصلية ويعزل فرق الصرف في حساباته المصنفة. الدفعة الأخيرة تغلق SDG وUSD بدقة، دون خلط دين افتتاحي مع فاتورة. سياسة SDG-only لا تخمن الدولار أو الصرف. يرفض المبلغ المتجاوز أو قليل الدقة، والتاريخ السابق للمصدر/آخر التسويات، والحساب غير النشط أو التابع لمؤسسة أخرى، والحقول المحمية.
- إعادة تشغيل تاريخ المصدر كاملاً للتحقق من الأطراف وحركة المخزون والقيود والتسويات وتسلسلها. حتى التقرير بتاريخ قديم يتحقق من الأحداث اللاحقة قبل اختيار التاريخ، فلا يخفي إثباتاً تالياً مكسوراً. التقرير الخالص يخرج opening/movement/closing والأعمار والاستحقاق ومراجع القيود مستقلة عن الأرصدة الحالية.
- إضافة نوعي قيد محجوزين `opening_batch` و`opening_settlement`؛ لا تسمح عملية journal.create الحالية بترحيلهما يدوياً. لا توجد صلاحية كتابة جديدة في هذا الفرع.

## التحقق

نجح `npm run check`: **211 وحدة/API**، منها 12 اختباراً جديداً؛ الأنواع والفحص الصارم والبناء ناجحة. تشمل الحالات أهلية المصادر والعزل والتكرار والتهيئة الصفرية، أصل الإثبات والعملتين والمخزون، الاستحقاقات وفرق الافتتاح وحد الحجم، تغيّر الأرصدة الحالية، فقد/تعديل القيود والأطراف والحركات، AR/AP والسداد النهائي، 72 تسلسلاً للقيم والأسعار، التحويل بين العملات، الحسابات/الصلاحية البنيوية/الدقة، SDG-only، العبث بأحداث لاحقة لتاريخ التقرير، المطابقة مع خطوط AR/AP في GL، واستقلال ترتيب مفاتيح JSON. CI الكامل ينتظر التأكيد لهذا الفرع.

C2.1 اكتمل في [CI 37688369294](https://github.com/mistertee1/Sodaflow/actions/runs/37688369294): 199 وحدة/API و26 Firestore و44 واجهة وصفر ثغرات إنتاج على `23492f1f3c0043d65399316b88ccd18c97acd18a`، وأصبح [PR25](https://github.com/mistertee1/Sodaflow/pull/25) جاهزاً للمراجعة.

## الحدود والخطوة التالية

هذه عقود قراءة/توليد إثبات خالصة غير موصولة بمخزن الإنتاج أو API. لا تمثل إثبات هوية أو صلاحية، ولا تحقق رصيد البنك المتاح للسداد. يجب أن يستخدم C2.2b بيانات المعاملة الطازجة، Owner الفعلي والتحقق الحديث والسبب، والعضوية والاشتراك والميزات والفترة المفتوحة وserver/rules authority وidempotency قبل إعادة المعاينة والترحيل. تبقى كل الكتابات في معاملة واحدة، وتتحقق المطابقة بعد بنائها قبل commit. حدود العقود: مصدر افتتاحي 97، أطراف القيد 100، دفعة افتتاح واحدة، 200 تسوية لكل طرف، 1200 صف لكل مجموعة في التحقق، و650KB لأساس الافتتاح. حدود restore الحالية أصغر ويجب تطبيقها أيضاً؛ الدفعات الأكبر تحتاج jobs/import مضبوطاً.

التحقق يثبت اتساق المستندات المحفوظة ولا يوقع ملفاً خارجياً أو يصادق على تاريخ مفبرك كاملاً. الاستعادة تحتاج metadata/counts وحفظ التدقيق ومنع إسقاط مجموعة مصدر كاملة؛ لا تكفي إعادة تشغيل العقود وحدها. إعادة تعيين المؤسسة يجب أن تشمل الأساس المتداخل ومراجع الهوية مع الحفاظ على الملكية والمرجع الأصلي للتدقيق. أرصدة العملاء الدائنة والموردين المقدمة والهجرة ذات التاريخ القائم ليست مشمولة بعقد البدء الحالي.

التالي C2.2b الترحيل الذري والتسويات والتقارير/المطابقة/الاستعادة وواجهة المساعد، ثم C2.3 رأس المال والمسحوبات. تبقى FX والأصول والإهلاك والضرائب والمقارنات في C، وD/E وExcel1–4 ومعايير الجاهزية التجارية. لم يتغير Super Admin أو المصادقة أو المزامنة أو Rules، ولم يحدث دمج أو كتابة إلى main أو نشر أو تعديل بيانات إنتاج. دمج سلسلة B3/C الكاملة إلى main يظل بيد المستخدم.
