1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
This comprehensive audit evaluates the readiness of the "Hesabak" (حسابك) SaaS financial
management platform at the Phase 2 milestone (Multi-Tenancy, Scalable SaaS Architecture,
RBAC, and Security Hardening).

Key Takeaways:
- Multi-Tenancy Architecture: The multi-tenant schema (/organizations/{orgId} and
  /user_organizations/{userId}/orgs/{orgId}) is fully defined in Firestore Rules and
  programmatically supported in the service layer (`organizationService.ts`). A safe,
  non-destructive migration pipeline from legacy /users/{userId} to /organizations/{orgId}
  is implemented.
- premature Phase 3 Accounting: Double-entry general ledger, chart of accounts, trial
  balance, and income statement were introduced prematurely by prior build steps. In
  strict accordance with the audit mandate, these features have been preserved intact and
  verified to be safely isolated under the tenant hierarchy without corrupting Phase 1
  or Phase 2 foundations.
- Critical Warnings Carried Forward:
  1. No Firebase Cloud Functions exist (`functions/` directory absent); financial logic
     relies on a hybrid of client-side Firestore transactions and an Express server.
  2. Receipts continue to be stored as Base64 strings in Firestore/localStorage rather
     than Firebase Cloud Storage (`STORAGE_STATUS = 'FIREBASE STORAGE: NOT DEPLOYED'`).
  3. Voiding a partially paid invoice reverses remaining debt but fails to automatically
     allocate already collected cash as customer store credit.
  4. Invoice numbering determines the sequence number in memory prior to entering
     Firestore transactions, presenting concurrency collision risks under high write loads.
  5. Query scalability is currently unbounded: `loadOrgData` executes unpaged `getDocs`
     over entire collections (invoices, products, customers, movements, journal entries).

Final Decision: PASS WITH WARNINGS
Commercial Launch Status: NOT READY — verification continues through remaining phases.

7. DATABASE / FIRESTORE REVIEW
--------------------------------------------------------------------------------
- Primary Hierarchy: `/organizations/{orgId}`
  Subcollections:
  * `members` (Tenant user access list with assigned roles)
  * `invitations` (Pending team invitations)
  * `settings` (Tenant-scoped currency, rounding, and branding parameters)
  * `customers` & `suppliers` (Counterparties)
  * `products` (Inventory catalog with stock tracking)
  * `invoices` (Sales ledger with frozen FX and status)
  * `payments` (Receipts and settlements)
  * `expenses` & `purchases` (Cost accounting)
  * `inventory_movements` (Append-only stock audit log)
  * `accounts` & `journal_entries` (Premature Phase 3 general ledger)
  * `audit_logs` & `idempotency` (Traceability and deduplication locks)
- Mapping Collection: `/user_organizations/{userId}/orgs/{orgId}`
- Legacy Collection: `/users/{userId}/*` (Preserved for zero data loss)
- Indexes (`firestore.indexes.json`):
  * Status: FILE ABSENT. No custom composite index definition file found.
  * Cost & Query Risk: Standard queries will require composite indexes once compound
    filters (e.g. `where('status', '==', 'paid').orderBy('created_at')`) are introduced.
- Query Scalability & Aggregation:
  * Current load in `AppContext.tsx` uses unpaged `getDocs` across entire collections.
  * Document Read Cost Projections:
    - 100 records: ~800 reads per session load (Negligible).
    - 10,000 records: ~80,000 reads per session load (High cost & memory latency).
    - 100,000 records: Exceeds client memory boundaries; unsustainable without query cursors.

9. OFFLINE / RETRY / IDEMPOTENCY REVIEW
--------------------------------------------------------------------------------
- Client Offline Support:
  * LocalStorage caching mirrors all state changes with tenant-isolated keys:
    `${LOCAL_STORAGE_KEY}_${orgId}_${collection}`.
  * Users can operate in guest mode or during transient disconnects.
- Operation Locks & Idempotency:
  * Each invoice and payment receives an `operation_id` / `idempotency_key`.
  * In-memory duplicate checks prevent double-submission on UI double-clicks.
  * Written to `/organizations/{orgId}/idempotency/{operationId}` inside Firestore transactions.


10. BACKUP / RESTORE REVIEW
--------------------------------------------------------------------------------
- Export Scope:
  * Fully serializes settings, customers, products, invoices, payments, expenses,
    inventory movements, accounts, and journal entries into a clean UTF-8 JSON structure.
  * Handles Arabic characters and complex descriptions seamlessly.
- Restore Validation:
  * Validates JSON schema, verifies data arrays, and executes safe non-destructive merges.
  * Reconciles inventory stock and maintains historical FX rates without overwriting.


11. MIGRATION REVIEW
--------------------------------------------------------------------------------
- Migration Service: Implemented in `organizationService.ts` (`migrateUserToOrganization`).
- Legacy Preservation: The user's legacy `/users/{userId}` documents are never deleted
  or modified destructively.
- Mapping: Copies data to `/organizations/org-{userId}/*`, tags records with `schema_version: 2`,
  and registers the user as the organization Owner in `user_organizations`.
- Idempotency: Can be executed multiple times safely; records are merged via `{ merge: true }`.

  * Automatic journal entries are generated on invoice creation and voiding.

13. PERFORMANCE / SCALE REVIEW
--------------------------------------------------------------------------------
- Simulation Estimate (SIMULATION ONLY):
  * At 10,000 invoices and 50,000 journal lines, transferring all documents to the browser
    client in `loadOrgData` would require ~45 MB of network payload and several seconds of
    main-thread JSON parsing.
  * Client-side pagination (`limit(50)` and `startAfter()`) must be implemented before
    Phase 4 production deployment.
  * Financial summaries (Dashboard Totals) should transition to Firestore `count()` /
    `aggregate()` queries or materialized counters in `meta/counters`.
