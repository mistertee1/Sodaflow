# تقرير B1 — الموردون والمشتريات والذمم الدائنة

التاريخ: 2026-10-05. الفرع: `codex/accounting-v2-b1-supplier-purchases`. الأساس: آخر main `ecee366e960a820b621c8dbded6909c43a4a3096` بعد دمج المستخدم A2 (#14). الحالة: منفذ؛ التحقق المحلي ناجح وCI قيد الانتظار. B1 جزء من B، وليس اكتمال المرحلة أو الوثيقة.

## التنفيذ

- سجل موردين قابل للبحث والتعديل والتعطيل، يتضمن الاتصال والرقم الضريبي والعملة وأجل السداد وحد الائتمان والملاحظات. الرصيد محسوب من القيود ولا يقبل تعديل العميل.
- فاتورة شراء نقدية/بنكية أو آجلة، من 1 إلى 100 بند؛ رقم فاتورة المورد فريد داخل المؤسسة لكل مورد، مع منع تكرار إعادة المحاولة. المستند المرحّل غير قابل للتحرير أو الحذف.
- الاستلام وتحديث المتوسط المرجح وقيد المخزون/AP أو الحساب النقدي المختار تتم ذرّياً. البنود المتكررة لنفس المنتج تُجمع قبل تحديث المخزون؛ تكلفة الشراء لا تُستنتج من سعر البيع.
- سداد جزئي أو كامل ومتكرر لكل فاتورة، بعملة السداد وسعر الصرف والتاريخ والطريقة والمرجع. الإقفال يستخدم القيمة الدفترية التاريخية للعملتين؛ فرق النقدية يُرحّل إلى ربح/خسارة صرف. ترتيب السندات محفوظ حتى عند تطابق الأوقات. الدفع المتزامن لا يستطيع تجاوز الدين.
- AP Aging حتى تاريخ محدد: Current و1–30 و31–60 و61–90 و90+. كشف مورد بفترة ورصيد افتتاحي وحركات ورصيد ختامي من GL؛ السداد اللاحق لا يغير الرصيد التاريخي المعروض.
- CSV وPDF عربي لكشف المورد، بعد قراءة خادم جديدة وصلاحية تصدير وسجل تدقيق للفترة. CSV يحفظ المعرّفات والعملتين منفصلتين ويعطّل النصوص التي قد تُفسّر كصيغ.
- المصروفات الآجلة الجديدة في V2 تستخدم 2140، وتُحفظ مصروفات 2110 القديمة كما كانت مع إظهار الجزء غير الموزع على فواتير الموردين. لا يُحوّل رصيد قديم أو يُنسب إلى مورد تخميناً. القيود اليدوية على 2110 ممنوعة في V2.
- مطابقة الشراء والسداد ومراجع المورد والمنتج والاستلام والقيود وAP control في العملتين؛ النسخة الاحتياطية تشمل المجموعات الثلاث الجديدة وتعيد فهرس مراجع المورد. النسخ القديمة بدون هذه المجموعات تُقبل كمجموعات فارغة فقط إذا كانت المطابقة سليمة.
- صلاحيات الخادم: Owner/Admin/Accountant للكتابة، Viewer للقراءة؛ Sales/Cashier لا يقرآن دفتر الموردين. انتهاء الاشتراك وFeature المحاسبة والمخزون والبريد والعضوية وفترة القفل مفروضة. قواعد Firestore الحالية تبقى كما هي: لا كتابة مباشرة، والمجموعات الجديدة متاحة عبر API فقط.

## حفظ التغييرات الأخرى

راجعت وأدرجت تغييرات main الجديدة الخاصة بالسوبر أدمن والباقات والمزامنة وNetlify. لم أستبدلها بالنسخة القديمة. أُضيفت اختبارات platformAdmin وplatformBilling الموجودة إلى check/CI. فحص البريد الجديد ظل مفروضاً على هويات السحابة؛ استُخدم ممثل محلي واضح لوضع الضيف حتى يبقى المحرك المحلي صالحاً، ولا يقبل API هوية من جسم الطلب.

## التحقق

- محلياً: الأنواع وstrict core و81 اختبار وحدة/API/سوبر أدمن وبناء الواجهة والخادم نجحت. 10 اختبارات B1 تغطي المشتريات، تكرار البنود، النقدي المخصص، AP/FX، التزامن، الأعمار والفترة، العزل والاشتراك، الاستعادة، API وترتيب التقريب.
- Playwright B1 على الموبايل نجح: مورد، إثبات/تفعيل V2، شراء، سداد جزئي، ضغط إرسال مزدوج، تنزيل CSV وPDF حقيقي. تمت مطابقة السجلات الناتجة.
- اختبار جديد لمحاكي Firestore يختبر استلام الشراء والسداد المتزامن الذري ومنع SDK للمجموعات الجديدة. Java 21 متاح في CI؛ البيئة المحلية Java 17، لذلك نتيجة المحاكي والمجموعة الكاملة للواجهة تنتظر CI.
- لا دمج أو كتابة main أو نشر أو تعديل قواعد أو بيانات إنتاج أو أموال حقيقية.

## الحدود والباقي

فواتير هذا الجزء تستقبل تكلفة مخزون صافية مثبتة؛ الضريبة القابلة للاسترداد والخصومات المستقلة ضمن مركز الضرائب C. حد ائتمان المورد محفوظ كبيان مرجعي؛ تطبيق السياسات والموافقات ضمن D. سداد سند واحد يخص فاتورة واحدة؛ يمكن تسجيل عدة سندات، والسداد المجمع لعدة فواتير ليس ضمن هذا الجزء. المردودات وإشعارات الدائن/المدين والرد النقدي ضمن B3، ولا توجد إزالة أو إعادة كتابة مستند مرحّل.

حد الاستعادة 350 سجلاً مع قيد إضافي لعدد كتابات فهارس المشتريات؛ ترحيل البيانات الكبيرة ضمن مراحل الوظائف. لا أدعي تحقق اتصال إنتاج أو قواعد منشورة؛ عائق Firestore API المذكور في تقارير التشغيل والسوبر أدمن يحتاج معالجة تشغيلية مستقلة. لا تزيل الاختبارات المحاكية هذا العائق.
