# سودافلو | SudaFlow

إدارة الفواتير والعملاء والمخزون والمحاسبة بالجنيه السوداني والدولار، بواجهة عربية RTL وهوية سودافلو.

## التشغيل

يتطلب Node.js 24. اختبارات Firestore تتطلب Java 21. الواجهة React/Vite، والخادم Express، والمصادقة Firebase Auth.

```sh
npm ci
cp .env.example .env
npm run dev
```

للتشغيل الإنتاجي على خادم Node:

```sh
npm run build
NODE_ENV=production npm start
```

يستخدم الخادم Application Default Credentials على خوادم Google أو ملف `GOOGLE_APPLICATION_CREDENTIALS`. **على Netlify يجب إضافة `FIREBASE_SERVICE_ACCOUNT_JSON` كمتغير بيئة سري يحتوي JSON الكامل لحساب خدمة Firebase**؛ لا تضفه إلى Git ولا تستخدم بادئة `VITE_`. يجب أن يكون حساب الخدمة من نفس مشروع Firebase الموجود في `firebase-applet-config.json`. يمكن تجاوز المشروع/قاعدة البيانات عبر `FIREBASE_PROJECT_ID` و`FIRESTORE_DATABASE_ID`. مفاتيح الخدمة و`BILLING_SIGNING_SECRET` لا تُرسل للمتصفح ولا تدخل Git.

حسابات البريد/كلمة المرور لا تنشئ مؤسسة ولا تبدأ مزامنة حتى يتم تأكيد البريد من رابط Firebase. التسجيل الجديد يقبل بريداً إلكترونياً حقيقياً فقط؛ تسجيل الدخول برقم الهاتف الاصطناعي يبقى للتوافق مع الحسابات القديمة ولا يمنح وصولاً سحابياً غير موثق.

**الواجهة الثابتة وحدها لا تكفي للحفظ السحابي:** يجب تشغيل Express ومسارات `/api` على نفس الأصل، ونشر القواعد بالتزامن معه. توجد خطوات التفعيل في [دليل التشغيل](docs/operations.md).

## التحقق

```sh
npm run check
npm run test:emulator
npx playwright install chromium
npm run test:ui
npm audit --omit=dev
```

`check` يفحص TypeScript، ثم يفحص محرك العمليات والخادم بوضع strict، ويشغّل اختبارات المحاسبة والصلاحيات والحفظ ويبني الإنتاج. اختبارات المحاكي تستخدم `demo-sudaflow` فقط. GitHub Actions يشغّل التحقق والمحاكي واختبارات المتصفح على طلبات الدمج.

## تنظيم الكود

- `src/domain`: التحقق، الحسابات المالية، العمليات الذرية، ومحرك الوضع المحلي.
- `server`: مصادقة الخادم، محول Firestore، المؤسسات، وتحقق الاشتراكات.
- `src/services/businessApi.ts`: حفظ مؤكّد، ومعرّفات إعادة المحاولة.
- `src/context/AppContext.tsx`: حالة الواجهة وجلب بيانات المؤسسة، دون كتابة مباشرة في Firestore.
- `src/components/accounting`: تقارير المحاسبة المفصولة عن النماذج.
- `public/brand` و`src/styles`: الشعار، الخط المحلي المرخّص، وقيم الهوية للثيمين.

## سلوك العمليات

الفاتورة والمخزون ورصيد العميل والقيد والسجل الرقابي والعدادات تُحفظ في معاملة واحدة. الخادم يعيد قراءة القيم عند التزامن ويعيّن رقم الفاتورة. إعادة طلب بنفس المعرّف والبيانات تعيد النتيجة نفسها؛ تغيير البيانات مع المعرّف ذاته مرفوض.

التحصيل يُسوّي الذمم بقيمتها التاريخية، ويسجّل النقد بسعر التحصيل وفروق العملة منفصلة. التدفق النقدي يعتمد حركة حسابات النقد والبنوك. السندات والقيود ثابتة؛ إبطال فاتورة غير محصّلة وعكس مصروف ينشئان قيداً عكسياً. الفاتورة المحصّلة تحتاج معالجة ردّ مبلغ موثّقة، ولا يُفترض حدوث ردّ نقدي بمجرد الضغط على الإبطال.

الفترات المقفلة تُفحص في الخادم. التحصيل الحالي لفاتورة قديمة ممكن إذا كان تاريخ السند في فترة مفتوحة؛ أصل الفاتورة لا يتغير.

## الهوية وبيانات المنشأة

الهوية: سودافلو | SudaFlow، «شغلك أوضح.» الأصول SVG والخط IBM Plex Sans Arabic مرخّص داخل `public/brand/licenses`. الفاتورة تصدر باسم المنشأة وشعارها، وسودافلو يظهر كتذييل للنظام. بيانات المتاجر المحفوظة لا تُعاد تسميتها. مفاتيح بيانات الضيف القديمة تُقرأ وتُحفظ في مخزن محلي ذري؛ لا تُرسل تلقائياً إلى مؤسسة سحابية.

تفاصيل مطابقة ملف PDF والحزمة الأصلية وتغطية الاختبارات في [توثيق تطبيق الهوية](docs/brand-implementation.md).

## حدود واضحة

- لا توجد بوابة دفع أو إرسال بريد دعم تلقائي: نموذج الدعم يؤكد حفظ الرسالة، وطلب تغيير الباقة يبقى معلقاً.
- الباقات المدفوعة تحتاج اعتماد خادمي موقّع. قيم الاشتراك القديمة المكتوبة من المتصفح لا تمنح حقوقاً مدفوعة.
- التصدير يشمل كامل البيانات المسموحة للدور. الاستعادة الذرية إلى مؤسسة فارغة فقط، بصيغة الإصدار 3، وبحد 350 سجلاً. النسخ الأكبر أو القديمة تحتاج إجراء ترحيل خادمي مُراجع.
- جلب الواجهة يشمل كامل السجلات المسموحة، بتصفح الصفحات داخلياً في الخادم. هذا يصلح دقة الإجماليات؛ المؤسسات الكبيرة جداً تحتاج لاحقاً استعلامات تقارير مجمّعة.
- لم تُنشر هذه التغييرات على قاعدة بيانات حية. البيانات التاريخية المتأثرة بالأخطاء السابقة تحتاج فحصاً قبل التفعيل؛ أُضيف إجراء فحص دون تعديل القيود.
