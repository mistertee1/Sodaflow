# تقرير C2.3.1 — أساس حساب رأس المال والمسحوبات

التاريخ: 2026-10-10. هذا جزء حسابي كامل محدد من C2.3، وليس اكتمال العمليات أو واجهتها أو قبول Render.

## التغيير
- معاينة حسابية خالصة دون كتابة أو منح صلاحية أو endpoint جديد. الإيداع يقابل حساب رأس المال 3100، والسحب يقابل المسحوبات 3200 ولا يدخل مصروف التشغيل أو فروق الصرف.
- SDG-only صريح؛ الإيداع مزدوج الدفاتر يتطلب سعر صرف مثبتاً. السحب يستخدم القيمة الدفترية التاريخية للحساب المالي ويحتفظ بباقي التقريب عند السحب النهائي، ولا يقبل سعر صرف جديداً.
- رفض الحقول المشتقة المصطنعة، حسابات المؤسسة الأخرى أو المكررة أو غير النشطة، وتصنيف التحكم الخاطئ أو القيود غير المتزنة أو ذات الحساب المفقود.
- فحص الفترة والإقفال القديم؛ رفض العمليات العادية داخل الإقفال المبدئي. منع العجز في كلا الدفترين عند التاريخ وكل إقفال يوم لاحق، حتى لو عاد الرصيد موجباً بعد ذلك.
- إدراج 8 اختبارات جديدة في npm test وفحص TypeScript الصارم. اختبارات MemoryStore ببيانات اصطناعية تثبت عدم الكتابة.

## حدود ومخاطر
الدالة لا تتحقق من جلسة مستخدم أو اشتراك، ولا يجوز استدعاؤها كتصريح مالي أو الثقة بمعاينة متصفح. الجزء التالي يجب أن يقرأ المصادر الكاملة داخل معاملة خادمية، يعيد التحقق من المالك والصلاحيات والفترة، ويسجل مصدر العملية والقيد والتدقيق وreceipt معاً؛ ويثبت السباقات والتكرار والrollback عبر MemoryStore وEmulator. لا تغييرات Rules أو منح صلاحيات في هذا الجزء.

قبول Render: معلق. التكامل ثبت ونجحت قراءة قائمة مساحات العمل، لكن تحديد مساحة العمل لم يؤكد بعد حسب متطلبات أداة Render؛ لا خدمة staging أو commit منشور أو مؤسسة اصطناعية تم التحقق منها. لا إعادة طلب دخول. المرحلة الحسابية غير موصلة بالتطبيق، لذلك ليست قابلة لقبول الحفظ على Render الآن.

يبقى C2.3.2 الأوامر المحمية والمصدر وإعادة التشغيل/المطابقة والنسخ الاحتياطي، ثم C2.3.3 الواجهة والصلاحيات واختبار Render، ثم C3-C6 وD وE وExcel1-4 والمؤجل والقبول النهائي. حافظ على ResilientStore والهوية والسوبر أدمن من main عند الدمج الذي ينفذه المستخدم؛ لا استبدال main بالفرع القديم.
