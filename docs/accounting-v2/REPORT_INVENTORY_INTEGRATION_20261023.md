# توافق المخزون والمشتريات مع أساس المحاسبة الحالي

2026-10-23 — المستخدم وحده يراجع ويدمج.

## النتيجة

يعرض المخزون الموردين ومنتجاتهم السابقة وفواتير المشتريات وسداد الذمم الدائنة في القسم نفسه. يمكن ترشيح المنتجات التي سبق شراؤها من المورد، واختيار المنتج الموجود، وإدخال الكمية وتكلفة الوحدة يدوياً. اختيار منتج لا ينسخ تكلفة شراء قديمة. تُحسب معاينة إجمالي SDG/USD بعقد التكلفة نفسه المستخدم في الخادم، وتُمنع التكلفة غير الصالحة قبل الإرسال.

يسمح نموذج إضافة المنتج في V2 بإدخال الكمية والتكلفة الافتتاحية، بما فيها الكمية الكسرية، ويطلب سبباً عندما تقرب قيمة أحد الدفترين إلى صفر. تُحفظ القيمة وحركة المخزون والقيد ذرّياً عبر العملية القائمة. الرصيد الافتتاحي المملوك يقابله حساب حقوق الملكية؛ لتوريد جديد يُنشأ المنتج بكمية صفر ثم تسجَّل فاتورة المورد، حتى تُثبت الذمة أو النقدية بصورة صحيحة. تتجدد حالة شاشة المخزون عند تبديل المؤسسة.

زر المالك «تفعيل المحاسبة V2 بعد المطابقة» باقٍ خلف حواجز الخادم وتوثيق التكلفة والمطابقة. الاختبار يفعله على مؤسسة اصطناعية فقط؛ لم يُفعّل حساب إنتاجي.

## أساس التكامل وحماية العمل السابق

PR135 اجتاز CI40001136418 وNode22 CI40001136284 على المصدر 6bde6814c4babf27a47bb15e834beb94a12b0ed0. دمجه المستخدم في فرع منع تكرار المنتجات، لا في main. لذلك أعيد تطبيق تعديل المخزون على أساس PR136، المصدر e2a1ffd4b79c5d3d63268f118a47e0a0006d7ca1، التابع لـmain307949a60f47aeeddc6ad3d44a1d35dd7e73edf7. يستهدف طلب المراجعة فرع PR136 إلى أن يدمج المستخدم الأساس.

حُفظت إصلاحات حفظ الفواتير وعقود الاستيراد في PR136 دون استبدال operations أو AppContext، وحُفظت أبعاد الشراء (الفرع ومركز التكلفة والمشروع). لا تغيير لمصادر Super Admin أو المزامنة أو قواعد Firestore. مصدر عملة العرض العام باقٍ في فرعه المنفصل؛ لا يدّعي هذا التكامل إدخاله إلى main.

## التحقق

ثلاثة سيناريوهات واجهة تستخدم API وOperations فعليين مع مصادقة محاكاة وMemoryStore معزول: كمية افتتاحية3.5 بتكلفة3500SDG و1.75USD وقيد حقوق ملكية واحد؛ إعادة شراء المنتج نفسه بكمية3 وتكلفة وحدة2000 مع مخزون5 وقيمة8000SDG و4USD وذمة الفاتورة الجديدة6000SDG دون منتج مكرر؛ وتفعيل V2 بواسطة المالك بعد المطابقة. اجتازت النسخة السابقة في PR135 الاختبارات الثلاثة ضمن92 اختبار واجهة.

أُبقي خادم الاختبار الاصطناعي مفتوحاً إلى انتهاء طلبات الواجهة الجارية قبل إغلاقه، لمعالجة سباق teardown المثبت سابقاً، دون تخفيف assertions المالية.

كشف CI40018398504 للأساس PR136 افتراضاً قديماً في اختبار إيقاف الضوابط التجارية: كان يتوقع أن كل مجموعة في snapshot الخادم متاحة أيضاً مباشرة من SDK. مجموعات إعدادات/مهام التصدير وسياسات الموافقة وجلسات الاستيراد التاريخي محمية عبر API فقط. يثبت الاختبار المصحح أن جميع الأدوار الفعلية، بما فيها العضو الموقوف، تستقبل بيانات المؤسسة عبر snapshot المصادق عليه، مع استمرار رفض القراءة المباشرة لهذه المجموعات وعدم تغيير العضوية أو بيانات الاشتراك. لم تُفتح صلاحية SDK جديدة.

نجح الفحص المحلي الكامل: TypeScript/core و455 وحدة/API و16 اختبار Netlify runtime والبناء. CI للتكامل قيد التنفيذ، ويتولى Firestore Emulator وPlaywright على المصدر الحالي؛ ستسجل نتيجته الفعلية في PROGRESS.json قبل تسليم المرحلة.

## الحدود وما بقي

لم يكتمل تنفيذ الوثيقة أو القبول التجاري. نقطة الاستئناف المحاسبية الأحدث هي PR126 وفرع codex/accounting-v2-excel4-historical-approval-ui-20261023، وليست C5 القديمة في تتبع main. إعادة CI39986838841 انتهت ملغاة أثناء اختبارات الواجهة؛ لا يُعد ذلك نجاحاً كاملاً. يبقى إلزام عقد المراجعة التاريخية خادمياً، واستعادة الجلسة/الإيصال الآمنة بعد reload، وبقية Excel4 وحزمة المراجع والتصدير المجدول وقبول البيئة المصادق عليه والمطابقة والاستعادة النهائية دون فروقات.

لم تُكتب تغييرات إلى main ولم يدمج الإيجنت PR أو ينشر تطبيقاً أو قواعد أو يغيّر بيانات إنتاج أو يرحّل أموالاً حقيقية. يلزم دمج المستخدم للأساس والتكامل، ثم قبول المؤسسة المستهدفة قبل وصف الوظيفة بأنها متاحة في الإنتاج.
