# تنفيذ Super Admin في SudaFlow

المستودع المرجعي: `mistertee1/Sodaflow`. العمل يبدأ من أحدث `main` ويحتفظ بالمحاسبة والهوية وإصلاحات المزامنة. طلب 2026-10-05 يعتمد الاختبارات قبل دمج كل مرحلة، ويلغي قيد عدم الاختبار السابق لهذا المسار.

| --- | --- | --- |
| 0 — المراجعة | إثبات الحالة الحالية وخطة قابلة للاستئناف | توثيق الاختبارات الحالية والفشل والعوائق دون ادعاء جاهزية الإنتاج |
| 1 — الهوية والصلاحيات | تحقق البريد، فصل Super Admin عن Owner/Admin، جلسة إدارة آمنة | رفض الهوية غير المؤكدة، claim وحده أو registry وحده لا يكفيان، منع الوصول المالي لشركة غير مملوكة، regression الحالية |
| 2 — إدارة الاشتراكات والباقات | حالات وتواريخ وتجديد وتمديد وتغيير باقة وتجربة مرة واحدة وسجل ذري | idempotency وrevision والتزامن والفشل الذري، فرض 100 فاتورة مدى الحياة ومقعد موظف واحد، features مباشرة من الباقة، منع التجاوز |

## الاستئناف وتنسيق العمل

- اقرأ `PROGRESS.json` و`REPORT.md` وأحدث main قبل كل جولة. لا تعتمد على بقاء مجلد التنفيذ أو node_modules في السحابة.
- احترم `activeRunId` و`leaseUntil` لتجنب جولة متزامنة. حرّر lease عند التسليم؛ إذا انتهت lease استأنف من آخر commit وفرع محفوظ.
- احفظ العمل غير المدمج في فرع واضح، واكتب أسماء الملفات المملوكة للمرحلة. لا تستخدم force push. إذا تغير main فراجع الملفات المتقاطعة وأعد الاختبارات المناسبة قبل الدمج.
- أنجز المرحلة واختبرها واحفظها في فرع وPR للمراجعة. اعتماد المستخدم الأحدث يجعل الدمج بيده فقط؛ لا تدمج أو تنشر إلى الإنتاج تلقائياً. سجّل الأدلة والنتيجة والحدود.
- اختبارات الكتابة تستخدم MemoryStore أو مشروع Emulator `demo-sudaflow`. لا تختبر بإنشاء فواتير أو مدفوعات فعلية في الإنتاج.
- عند بقاء عوائق خارجية فقط، حرّر lease وعلّق الأتمتة وأرسل تقريراً واضحاً. لا تكرر طلب الدخول الذي رفضته المراجعة التلقائية دون تصريح جديد.

## نتيجة المسار حتى 2026-10-05

مراحل المصدر 1–4 مكتملة ومدمجة، بنتيجة نهائية 93 اختبار خادم و20 اختبار Firestore و32 اختبار واجهة ناجحة. راجع [التقرير](REPORT.md) للـ commits والأدلة، و[دليل التشغيل](OPERATIONS.md) لشروط التفعيل.

المرحلة 5 تبقى معطلة: الفحص الحالي يؤكد عدم وجود قاعدة `(default)` في sodaflow، ومشروع النشر غير ظاهر في تكامل Netlify، ولم يُحدد UID إدارة مؤكد. يلزم تحديد القاعدة التي تحتوي بيانات العملاء قبل أي تغيير إعداد أو ترحيل. لا يُعاد مسار بناء المصدر عند الاستئناف؛ يبدأ الاستئناف بإثبات تغير متطلبات الإنتاج ومراجعة أحدث main ثم بوابة التشغيل فقط.

## تحديث 2026-10-10 — Render

هدف التشغيل الجديد هو `https://sudaflow.onrender.com` في My Workspace. الخدمة الحالية تتبع `codex/wafer-ux-phase1` ولا تتبع main. لا تغيّر خدمة الإنتاج أو خدمة اختبارات المحاسبة.

المرحلة 5a تضيف ضمان مصدر البيانات: رفض Firestore لا يجوز أن ينشئ شركة أو اشتراكاً أو فواتير ناجحة في ملف محلي. احتفظ بأي ملف محلي موجود للفحص والترحيل المراجع لاحقاً. اختبر فشل الهوية/الكتابة والتعافي الفعلي و100 فاتورة والصلاحيات في MemoryStore وEmulator `demo-sudaflow`، ثم نفّذ القبول على خدمة Render منفصلة بلا أسرار إنتاج أو منافذ Emulator عامة.

المرحلة 5b مستقلة: قبول ومراجعة الفرع، صلاحيات Firebase صحيحة لقاعدة بيانات العملاء الموجودة، UID إدارة مؤكد، ثم معاينة وترحيل معتمد وRules وتشغيل فعلي. readiness الحالي يرجع 503 في فحص بيانات دخول Firebase قبل اختبار Firestore؛ تشخيص عدم وجود القاعدة من 5 أكتوبر تاريخي ويحتاج إعادة تحقق بعد حل الهوية. لا تفترض عودة القاعدة أو نجاح المزامنة بمجرد فتح صفحة HTML.

الفرع يعتمد على PR38 لإرجاع lock دون تحديث الاعتمادات. سجل CI38032227589 على الأساس يرصد 44 اختبار UI ناجحاً و6 فاشلة في الفواتير/الهوية؛ لا تعطلها أو تنسبها إلى هذا التغيير. بوابة الدمج النهائي تبقى مغلقة حتى نجاح regression اللازمة على النتيجة التي سيراجعها المستخدم.
