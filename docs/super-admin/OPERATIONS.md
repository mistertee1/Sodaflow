# تشغيل Super Admin في الإنتاج

هذه خطوات تفعيل فني منفصلة عن قبول المصدر. نتائج الاختبارات والنسخ المدمجة في [REPORT.md](REPORT.md)، وحالة الاستئناف في [PROGRESS.json](PROGRESS.json). لا يبدأ نشر أو ترحيل إنتاجي بمجرد نجاح GitHub checks.

## المتطلبات الحالية

فحص 2026-10-05 أعاد `/api/health/ready` بحالة HTTP 503 ورمز `firestore_database_missing`. قراءة Google Firestore المباشرة أكدت: `The database (default) does not exist for project sodaflow`. النسخة الحية ما زالت `3.0.3-netlify`، بينما علامة الإصلاح المطلوبة في المصدر `2026-10-05-central-sync-recovery`. تكامل Netlify المتاح لم يعرض مشروع sodaflow. لم يُحدد UID مسؤول المنصة.

يجب أولاً تحديد القاعدة التي تحتوي بيانات العملاء التاريخية واستعادة وصول الخادم إليها، ومراجعة تطابق إعداد الواجهة والخادم والقواعد. لا يُعتبر إنشاء قاعدة فارغة أو تغيير المشروع إلى نسخة ZIP قديمة إصلاحاً للمزامنة. الإعداد الحالي يستهدف `sodaflow` والقاعدة `(default)`؛ أي تصحيح للاسم أو المشروع يحتاج مراجعة متناسقة تحفظ البيانات وتعيد اختبارات الجاهزية. Storage غير جاهز أيضاً؛ هذا يخص رفع الصور ولا يمنع وحده مزامنة الفواتير.

## بوابة قبول المصدر

تشغّل CI الحالية Node 24 وJava 21، وفحص الأنواع والبناء والاختبارات. الكتابة الآلية تستخدم MemoryStore أو Firestore Emulator في `demo-sudaflow` فقط:

```sh
npm ci
npm run check
npm run test:emulator
npx playwright install --with-deps chromium
npm run test:ui
```

قبول المرحلة 4: 93 اختبار خادم، 20 اختبار Firestore، و32 اختبار واجهة ناجحة. المحاكي يثبت السلوك والصلاحيات المختبرة؛ لا يثبت نشر الفهارس المركبة أو جاهزية الإنتاج أو جلسة العميل الفعلية. ابدأ من أحدث main وراجع ملفات أي إيجينت آخر قبل النشر؛ لا تستخدم force push.

## نافذة التفعيل الفني

1. أعد فحص `/api/health/ready` من الموقع و`npm run billing:readiness` من بيئة الاعتماد المصرح بها. يجب أن تنجح Firebase وFirestore؛ راجع أخطاء القاعدة أو المشروع أو الاعتماد قبل أي ترحيل.
2. خذ نسخة احتياطية من القاعدة الأصلية، وسجل هوية المشروع والقاعدة والنسخة المنشورة. راجع السجلات المالية الحالية باستخدام أداة التدقيق، دون كتابة تسويات لإخفاء الفروقات.
3. شغّل `npm run billing:migrate` للمعاينة. وضع المعاينة لا يكتب الباقات أو الشركات أو الاستخدام أو الأحداث. رمز الخروج 2 يعني شركات تحتاج مراجعة؛ راجع معرّفاتها وأسبابها. توفير `BILLING_SIGNING_SECRET` السابق مطلوب للتحقق من العقود القديمة الموقعة، وليس لإنشاء عقد جديد.
4. بعد مراجعة المعاينة والنسخة الاحتياطية فقط، شغّل `npm run billing:migrate -- --apply`. كل شركة تُرحّل بمعاملة ذرية مستقلة؛ العملية على جميع الشركات ليست معاملة واحدة. إذا تعثرت شركة تبقى الشركات التي نجحت مطبقة، ويظهر الملخص والمعرّفات المرفوضة. إعادة التشغيل تحفظ الاستهلاك ولا تكرر ترحيل الشركة المكتملة. لا تستبدل خطط الإدارة المعدلة.
5. حدد UID مسؤول المنصة صراحةً، وتحقق من البريد والحساب الفعّال. شغّل `npm run billing:bootstrap -- EXACT_VERIFIED_UID` للمعاينة، ثم الأمر نفسه مع `--apply` بعد اعتماد هذا الحساب. لا يُستنتج المسؤول من أول تسجيل أو دور Owner. يتطلب الوصول claim من نوع boolean بقيمة true وسجلاً فعّالاً بدور super_admin؛ حدّث جلسة الحساب بعد التعيين.
6. انشر الواجهة وAPI من النسخة نفسها إلى مشروع SudaFlow الصحيح، وانشر Rules والفهارس عبر `npm run deploy:firebase:rules` في نافذة منسقة بعد نجاح جاهزية الخادم والترحيل. قاعدة Firestore تمنع كتابة المتصفح؛ يجب أن يكون API المركزي عاملاً قبل بدء استخدام الواجهة. تحقق من اكتمال إنشاء الفهارس في المشروع قبل اعتماد البحث والتصفية المركبة.
7. أثبت نسخة الإصلاح في HTML و`/api/health` وجاهزية `/api/health/ready`. وجود Commit على main أو حالة build ناجحة لا يثبت نشر الموقع.

الـ workflow اليدوي `Deploy Firebase rules` يتضمن ترحيلاً تجارياً وتعيين claims عند إدخال UID. لا يُستخدم كاختبار أو وسيلة تجاوز لمراجعة المعاينة. لم يُشغّل أثناء هذه المراحل.

## قبول التشغيل الحي

نفّذ الاختبارات التي تكتب في شركة اصطناعية منفصلة ومصرح بها. لا تنشئ فواتير أو سندات عملاء حقيقيين لمجرد الاختبار. استخدم سجلات العميل الحقيقية للقراءة والتأكد من أن التاريخ والهوية والعدادات محفوظة.

| السيناريو | النتيجة المطلوبة |
| --- | --- |
| بريد غير مؤكد أو Company Owner يزور `/super-admin` | رفض الوصول للإدارة التجارية |
| مسؤول مؤكد مع claim وسجل فعّال | الأقسام الخمسة والبحث والتصفية والسجل تعمل |
| تفعيل أو تمديد ثم انقطاع الرد وإعادة نفس الطلب | تعديل واحد وحدث واحد وrevision مزامنة واحدة |
| انتهاء أو تعليق الاشتراك | التاريخ التشغيلي متاح، والعمليات المحمية مرفوضة من الخادم |
| Free يصل إلى 100 فاتورة أو يغيّر الشهر أو يلغي فاتورة | الفاتورة 101 مرفوضة، والاستهلاك لا يصفر |
| المالك يدعو موظفاً إضافياً | مقعد المالك ومقعد موظف واحد؛ الدعوة المعلقة تحجز المقعد |
| تجربة لشركتين لنفس المالك | تجربة واحدة لمدة سبعة أيام |
| سحب سجل المسؤول أو تعطيل feature | الطلب التالي يرفض الصلاحية المسحوبة أو الميزة المعطلة |
| مسؤول المنصة يطلب تفاصيل مالية لشركة أخرى | رفض؛ إدارة الاشتراك لا تمنح عضوية مالية |
| إعادة تحميل العميل أو عودة الاتصال | snapshot مؤكد من API، واستعادة متابعة revision، بدون استبدال البيانات بكاش قديم |

سجل الإصدار والنتيجة والتاريخ وما بقي غير متحقق في REPORT، ثم اجعل `productionValidated` true فقط بعد اجتياز هذه البوابة. لا توجد بوابة دفع أو Webhook عام مفعّل؛ الربط اللاحق يستدعي الخدمة المركزية بعد تحقق الخادم من توقيع المزود ومعرّف الحدث، مع method وproviderReference وسجل ذري.

## إدارة الاشتراكات اليومية

بعد قبول التشغيل، تغيّر إدارة المنصة الباقات والحالات والتواريخ والميزات وتعالج طلبات الشركات من `/super-admin`. Firebase Console للإدارة الفنية والطوارئ. القيم القديمة والجديدة والفاعل والسبب والطريقة تسجل داخل معاملة التعديل؛ لا يستطيع Company Admin كتابة خطة أو تاريخ اشتراك مباشرة. إيقاف باقة يمنع تفعيلها وتجديدها حديثاً؛ لا يمحو عقودها الحالية أو تاريخ الشركات.
