## التغييرات

- تبويب عربي مستقل للأرصدة الافتتاحية والسداد، متاح للمالك والمحاسب وفق صلاحيات الاشتراك؛ لا حفظ افتتاحي للمحاسب.
- بنود متعددة للنقدية والبنوك، أرصدة العملاء والموردين مع الاستحقاق والمرجع، والمخزون مع الكمية وتكلفة الوحدة. دعم SDG فقط أو دفترين بأسعار صرف صريحة.
- معاينة محمية من الخادم تعرض الأصول والالتزامات ورأس المال وفرق حقوق الملكية ومجاميع القيد لكل دفتر؛ لا تكتب المعاينة في البيانات المالية.
- تغيير المدخلات أو إصدار البيانات يبطل المعاينة، واستجابة معاينة قديمة لا تعتمد مدخلات جديدة. حماية انتقال المؤسسة والجلسة قبل وبعد الطلب.
- حفظ افتتاحي بعد تحقق المالك الحديث عبر طريقة الحساب المرتبطة، أو تأكيد موسوم للتجربة المحلية فقط؛ يُرسل hash المعاينة لمحرك الحفظ الذري الموجود.
- إعادة استخدام حوار تحقق المالك مع نصوص خاصة للعملية؛ سلوك إقفال الفترات يظل الافتراضي. سبب التأكيد يجب أن يطابق سبب المعاينة المسجل.
- تحصيل أو دفع الرصيد الافتتاحي من حساب مالي محدد، مع تاريخ ومبلغ ومرجع وسبب وسعر صرف عند الحاجة. الخادم يتحقق من الرصيد والتسلسل والسيولة في الدفترين.
- منع النقر المتكرر أثناء الحفظ، مع الاحتفاظ بمعرف الطلب عند إعادة محاولة نفس البيانات بعد نتيجة غير مؤكدة. المسار السحابي يستخدم آلية idempotency القائمة.
- إضافة ثلاث حالات Playwright: الدورة الافتتاحية/التحصيل/إعادة التحميل على الهاتف؛ فرق حقوق الملكية وإبطال المعاينة؛ معاينة المحاسب دون صلاحية حفظ المالك.

## دمج ومخاطر

هذا PR متراكب فوق فرع C2 القديم ويحتوي تغييرات هذه الجولة فقط. `main` الحالي عند `2f0ac961a755ca1ddddb17fbbbf5dffc2085e0ab` يختلف عن سلسلة المحاسبة السابقة وله تحديثات للشعارات وResilientStore. دمج الفرع المتراكب في main يحتاج مراجعة ودمج تغييرات المزامنة الحديثة وإعادة الاختبارات على النتيجة؛ لا تنسخ نسخة هذا الفرع كاملة فوق main.

فحص أحدث main في GitHub Actions (run 37992458411) فشل عند setup-node بسبب غياب ملف تثبيت التبعيات package-lock.json قبل تنفيذ اختبارات الكود؛ لا يدل هذا على فشل اختبارات المحاسبة لكنه يعني أن main الحالي غير متحقق آلياً. رابط الدليل: https://github.com/mistertee1/Sodaflow/actions/runs/37992458411 .

نجاحات المراحل السابقة في PROGRESS دليل تاريخي على فروعها وليست إثباتاً أنها كلها مدمجة في main أو منشورة. فرع C2 يشمل شغل B/C السابق الذي لا يظهر كاملاً في سجل main.

المتبقي: اختبار قبول Render، ثم C2.3 رأس المال والمسحوبات، C3–C6، D، E، Excel1–4، المرفقات المؤجلة، وسيناريو الإطلاق التجاري مع صفر فروقات وBackup/Restore ومراجعة المستخدم.

## بيئة قبول Render — توجيه المستخدم

اختبارات القبول للنسخة المنشورة ستُنفذ على Render. CI والمحلي أدلة هندسية للكود، ولا تعني نجاح نشر Render. لم يوجد رابط Render أو service ID في المستودع أو السياق السابق، وتكامل Render المتاح غير مربوط بالحساب عند التحقق؛ قُدم اقتراح الربط للمستخدم. اختبار Render الفعلي ينتظر الربط وتحديد خدمة staging/preview المربوطة بفرع المرحلة أو commit موثق. يجب استخدام مؤسسة وحسابات اختبار اصطناعية في بيئة منفصلة عن بيانات العملاء؛ لا يغيّر هذا التوجيه حظر نشر الإنتاج أو دمج main تلقائياً.

تابع التطوير المستقل في فروع مراجعة، وسجل نتيجة Render كقبول مستقل عند توفر الوصول؛ لا تدّع نجاحه قبل تنفيذ سيناريوهات الحفظ والسداد والصلاحيات والمزامنة وإعادة التحميل على الخدمة المستهدفة.
