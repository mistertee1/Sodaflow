# مقارنة مزامنة Hesabak وSudaFlow — 2026-10-05

المصدر المرجعي: `Hesabak-main.zip` الذي قدمه المستخدم. المشروع القديم يتصل بـ`hesabak-b9658`، بينما الإنتاج الحالي يتصل بـ`sodaflow` وقاعدة `(default)`. نُقلت طريقة الاتصال ولم تتغير هوية مشروع Firebase أو مسارات الشركات الحالية. نقل البيانات بين المشروعين يحتاج إجراء مستقل موثق؛ تغيير config لا ينقل المستخدمين أو سجلاتهم.

## ما نُقل إلى المسار الحالي

- تهيئة Firestore باستخدام `experimentalForceLongPolling: true` كما في النسخة القديمة، مع تحديد القاعدة من إعداد المشروع.
- اكتشاف الشركات الموجودة عبر Firebase Web SDK قبل الاتصال بـAdmin API، حتى لا يتعطل تحميل مؤسسة متاحة للمستخدم بسبب صلاحية حساب خدمة الخادم.
- بعد توقف realtime listener، قراءة revision من Firestore مباشرة ثم fallback إلى endpoint الموثق عند رفض Security Rules فقط. أُبقيت مراقبة الإيجنت الآخر وإعادة المطابقة عند التركيز وعودة الاتصال وكل 30 ثانية.
- الاحتفاظ بمعرّف الطلب نفسه أثناء نتيجة الحفظ غير المؤكدة، ومسحه بعد نجاح SDK أو API. تعطل localStorage لا يمنع الحفظ؛ يحتفظ التطبيق بالمعرّف في الذاكرة لإعادة المحاولة ضمن الجلسة، ولا يضمن بقاءه بعد إعادة تحميل المتصفح إذا كان التخزين محجوباً.

## حدود التوافق

النسخة القديمة تقرأ وتكتب `users/{uid}` وتزامن المصفوفات المحلية سجلاً بعد سجل. المسار الحالي يحفظ الفاتورة والمخزون والذمم والقيد والعدادات في معاملة واحدة داخل `organizations/{id}`. نسخ حلقات setDoc القديمة سيكسر الذرية ومشاركة الشركة ويستبدل سجلات سحابية بقيم محلية قديمة؛ لذلك احتُفظ بمحرك المعاملات الحالي.

لم تُنسخ قاعدة السماح الشامل لكل مسارات المستخدم من المشروع القديم. الحفظ المباشر الحالي يستمر تحت قواعد الشركات والأدوار الموجودة؛ لا يعالج تعديل هذه القواعد رفض IAM لحساب خدمة Admin، لأنه يتجاوز Security Rules. تهيئة الشركات الجديدة وقبول الدعوات ورفع الصور والإدارة المركزية ما زالت تحتاج الخادم. إذا كانت الشركات الحالية غير متاحة عبر SDK ولا API فلن ينشئ التطبيق شركة بديلة لإخفاء فشل القراءة.

## التحقق والتفعيل

فحص TypeScript العادي وstrict وبناء الواجهة والخادم مطلوبان قبل النشر. هذه الجولة لا تشغّل الاختبارات الآلية وفق توجيه المستخدم السابق. علامة الإصدار: `2026-10-05-legacy-sdk-sync`.

التحقق الفعلي للمزامنة يتطلب دخول حساب قائم مؤكد البريد، مشاهدة بيانات المؤسسة مع حالة المزامنة، ثم إعادة تحميلها أو فتحها من جهاز آخر. لا يُعد نجاح البناء أو `/api/health` أو العرض كضيف إثباتاً للحفظ السحابي. لا تُنشأ فواتير أو سندات حقيقية لمجرد التحقق.

إدارة الاشتراكات محفوظة في فرع مستقل. يجب الحفاظ على إصلاحات هذا المستند عند الدمج، وتفعيل صلاحية Admin في Firestore والترحيل والقواعد المركزية قبل تشغيل المسار المالي المحمي في ذلك الفرع.
