# سودافلو | SudaFlow

إدارة الفواتير والعملاء والمخزون والمحاسبة بالجنيه السوداني والدولار، بواجهة عربية RTL وهوية سودافلو.

## التشغيل

يتطلب Node.js 24. اختبارات Firestore تتطلب Java 21. الواجهة React/Vite، والخادم Express، والمصادقة Firebase Auth.

```sh
npm ci
cp .env.example .env
npm run dev
```

للتشغيل الإنتاجي على خادم Node:

```sh
npm run build
NODE_ENV=production npm start
```

يستخدم الخادم Application Default Credentials على خوادم Google أو ملف `GOOGLE_APPLICATION_CREDENTIALS`. **على Netlify يجب إضافة `FIREBASE_SERVICE_ACCOUNT_JSON` كمتغير بيئة سري يحتوي JSON الكامل لحساب خدمة Firebase، بنطاق Functions وفي سياق Production، ثم إعادة النشر**؛ لا تضفه إلى Git ولا تستخدم بادئة `VITE_`. يجب أن يكون حساب الخدمة من نفس مشروع Firebase الموجود في `firebase-applet-config.json` (`sodaflow`). إذا كان `FIREBASE_PROJECT_ID` موجوداً يجب أن يطابق مشروع الواجهة؛ القيم القديمة تُرفض كخطأ إعداد، لا كجلسة دخول غير صالحة. يستخدم مشروع الإنتاج الحالي قاعدة Firestore الافتراضية `(default)`، ويمكن تحديد قاعدة أخرى عبر `FIRESTORE_DATABASE_ID` عند الحاجة. مفاتيح الخدمة و`BILLING_SIGNING_SECRET` لا تُرسل للمتصفح ولا تدخل Git.

حسابات البريد/كلمة المرور لا تنشئ مؤسسة ولا تبدأ مزامنة حتى يتم تأكيد البريد من رابط Firebase. التسجيل وتسجيل الدخول بكلمة المرور يعتمدان على بريد إلكتروني حقيقي فقط؛ لا يوجد مسار تسجيل دخول برقم الهاتف.

`GET /api/health` يؤكد تشغيل الدالة ويعرض معرّفات المشروع والقاعدة دون اختبار الوصول. `GET /api/health/ready` يختبر اعتماد Firebase وقراءة Firestore والوصول إلى حاوية Storage فعلياً، دون كتابة أو إرجاع بيانات المستخدمين. يعيد `ready` عند نجاحها، و`degraded` إذا كانت Firestore جاهزة وStorage غير جاهز، و`error` عند تعطل الاعتماد أو Firestore. تُخزّن نتيجة الفحص مؤقتاً لمدة 30 ثانية. عند فشل تحميل المؤسسة الأولي يعاد التحميل عند عودة الاتصال أو التركيز على الصفحة. بعد التحميل، يراقب التطبيق عدّاد revision عبر Firestore realtime listener ويعيد جلب snapshot عند وصول تعديل أحدث.

**هذا الفرع ينقل الحفظ المالي إلى API الخادم لفرض الاشتراك والحدود داخل معاملات Firestore.** القواعد تمنع الكتابة المباشرة من المتصفح؛ يبقى realtime listener لمراقبة revision والكاش للعرض فقط. لا تدمج أو تنشر هذا الفرع قبل إصلاح وصول حساب الخدمة إلى Firestore وترحيل الاشتراكات ونشر القواعد والفهارس وفق [دليل التشغيل](docs/operations.md). إصلاح المزامنة المنشور في `main` يحتفظ بالمسار المباشر الحالي حتى اكتمال التفعيل. تفاصيل تسليم العمل للإيجنت الآخر في [ملاحظات التنسيق](docs/billing-handoff.md).

## التحقق

```sh
npm run check
npm run test:emulator
npx playwright install chromium
npm run test:ui
npm audit --omit=dev
```

`check` يفحص TypeScript، ثم يفحص محرك العمليات والخادم بوضع strict، ويشغّل اختبارات المحاسبة والصلاحيات والحفظ ويبني الإنتاج. اختبارات المحاكي تستخدم `demo-sudaflow` فقط. GitHub Actions يشغّل التحقق والمحاكي واختبارات المتصفح على طلبات الدمج.

## تنظيم الكود

- `src/domain`: التحقق، الحسابات المالية، العمليات الذرية، ومحرك الوضع المحلي.
- `server`: مصادقة الخادم، محول Firestore، المؤسسات، وإدارة الاشتراكات المركزية.
- `src/services/firebaseSync.ts`: قراءة وحفظ عبر API ومراقبة revision عبر Firestore.
- `src/services/businessApi.ts`: الطلبات الموثقة ومعرّفات إعادة المحاولة دون تكرار العمليات.
- `src/context/AppContext.tsx`: حالة الواجهة وتطبيق التغييرات المؤكدة القادمة من Firestore.
- `src/components/accounting`: تقارير المحاسبة المفصولة عن النماذج.
- `public/brand` و`src/styles`: الشعار، الخط المحلي المرخّص، وقيم الهوية للثيمين.

## سلوك العمليات

الفاتورة والمخزون ورصيد العميل والقيد والسجل الرقابي والعدادات تُحفظ في معاملة واحدة. الخادم يعيد قراءة القيم عند التزامن ويعيّن رقم الفاتورة. إعادة طلب بنفس المعرّف والبيانات تعيد النتيجة نفسها؛ تغيير البيانات مع المعرّف ذاته مرفوض.

التحصيل يُسوّي الذمم بقيمتها التاريخية، ويسجّل النقد بسعر التحصيل وفروق العملة منفصلة. التدفق النقدي يعتمد حركة حسابات النقد والبنوك. السندات والقيود ثابتة؛ إبطال فاتورة غير محصّلة وعكس مصروف ينشئان قيداً عكسياً. الفاتورة المحصّلة تحتاج معالجة ردّ مبلغ موثّقة، ولا يُفترض حدوث ردّ نقدي بمجرد الضغط على الإبطال.

الفترات المقفلة تُفحص في الخادم. التحصيل الحالي لفاتورة قديمة ممكن إذا كان تاريخ السند في فترة مفتوحة؛ أصل الفاتورة لا يتغير.

## الهوية وبيانات المنشأة

الهوية: سودافلو | SudaFlow، «شغلك أوضح.» الأصول SVG والخط IBM Plex Sans Arabic مرخّص داخل `public/brand/licenses`. الفاتورة تصدر باسم المنشأة وشعارها، وسودافلو يظهر كتذييل للنظام. بيانات المتاجر المحفوظة لا تُعاد تسميتها. مفاتيح بيانات الضيف القديمة تُقرأ وتُحفظ في مخزن محلي ذري؛ لا تُرسل تلقائياً إلى مؤسسة سحابية.

تفاصيل مطابقة ملف PDF والحزمة الأصلية وتغطية الاختبارات في [توثيق تطبيق الهوية](docs/brand-implementation.md).

## حدود واضحة

- لا توجد بوابة دفع أو إرسال بريد دعم تلقائي: نموذج الدعم يؤكد حفظ الرسالة، وطلب تغيير الباقة يبقى معلقاً.
- `/super-admin` يتطلب claim موثقاً وسجلاً فعالاً في `platformAdmins`؛ Owner وAdmin المؤسسة لا يمنحان صلاحية المنصة. تغيير الاشتراك والباقة يسجّل القيم القديمة والجديدة في سجل مركزي ضمن نفس المعاملة.
- Free تسمح بـ100 فاتورة طوال عمر المؤسسة والمالك مع موظف إضافي واحد. الدعوات المعلقة تحجز مقاعد. Trial سبعة أيام ومرة واحدة للمالك؛ الاستخدام لا يسحب دور Owner.
- التوقيع القديم يُستخدم للتحقق من الاشتراكات السابقة أثناء الترحيل فقط. الحماية الجديدة تقرأ الباقة المركزية وحالة المؤسسة وتاريخ الانتهاء في الخادم.
- حدود الفروع والمخازن محفوظة في الباقات، لكن المنتج الحالي لا يتضمن إدارة كاملة للفروع والمخازن. إضافة flag جديد لا تنشئ وظيفة جديدة تلقائياً.
- التصدير يشمل كامل البيانات المسموحة للدور. الاستعادة الذرية إلى مؤسسة فارغة فقط، بصيغة الإصدار 3، وبحد 350 سجلاً. النسخ الأكبر أو القديمة تحتاج إجراء ترحيل خادمي مُراجع.
- جلب الواجهة يشمل كامل السجلات المسموحة، بتصفح الصفحات داخلياً في الخادم. هذا يصلح دقة الإجماليات؛ المؤسسات الكبيرة جداً تحتاج لاحقاً استعلامات تقارير مجمّعة.
- لم تُفعّل إدارة الاشتراكات المركزية على قاعدة الإنتاج. أُجري فحص TypeScript وبناء الإنتاج دون تشغيل الاختبارات الآلية بناءً على طلب المستخدم. مجموعات اختبارات المزامنة المباشرة القديمة تحتاج تحديث توقعاتها قبل اعتماد الفرع إنتاجياً.
