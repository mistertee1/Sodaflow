1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
This audit evaluates the Professional Accounting Engine of "Hesabak" (حسابك) exactly
as it currently exists. The double-entry general ledger, chart of accounts, trial
balance, and income statement were added prematurely by previous build iterations.
In strict compliance with instructions, these features have been preserved intact
without deletion, rollback, or redesign.

Key Findings & Architectural Evaluation:
- Double-Entry General Ledger: The engine correctly enforces the fundamental accounting
  equation (Total Debits = Total Credits) across both Sudanese Pounds (SDG) and US Dollars
  (USD). Automatic journal vouchers (JVs) are generated upon invoice creation, invoice
  voiding, payment receipt recording, and expense logging.
- Chart of Accounts (COA): Standardized 5-tier classification (Assets, Liabilities,
  Equity, Revenue, Expense) tailored for retail merchants with optional default accounts
  (Bankak, Fawry, Cash USD, Cash SDG, Merchandise Inventory). Custom accounts can be created.
- Immutability & Firestore Rules: General ledger journal entries (`/journal_entries/{id}`)
  are strictly append-only in `firestore.rules` (`allow update, delete: if false`).
  Voiding an invoice generates a compensating reversal journal voucher (`JV-REV-*`)
  rather than deleting historical records.
- Warnings & Critical Scope Deficiencies Carried Forward:
  1. Accounts Payable & Purchases: AP account (2110) exists in COA, but there is NO
     dedicated operational Purchases or Suppliers subledger in the UI/data model.
  2. Customer Returns / Credit Notes: No separate return module exists; returns are
     only handled via full invoice voiding (`voidInvoice`).
  3. Realized FX Variance on Settlements: Cross-currency payments calculate equivalents
     using the payment exchange rate, but do not yet automatically calculate and post
     unrealized-to-realized FX gain/loss variance between invoice issue date and payment date.
  4. Accounting Periods & Period Closing: Fiscal year start exists as a configuration
     setting, but period locking/closing to prevent back-dated posting is NOT IMPLEMENTED.
  5. Atomicity & Split-Write Risk: In `createInvoice`, operational documents are committed
     in a Firestore transaction, but the journal entry is written in a sequential
     `setDoc` post-transaction, risking desynchronization on network interruption.
  6. Expense Deletion Orphan Risk: `deleteExpense` deletes the expense document from
     Firestore without creating a compensating reversal JV.
  7. Financial Statements: Trial Balance and Income Statement (P&L) are fully computed;
     Balance Sheet and Cash Flow Statement are not yet exposed as dedicated statement tabs.

Final Decision: PASS WITH WARNINGS
Commercial Launch Status: NOT READY — accounting reconciliation and remaining production
gates are still required.

4. DOUBLE-ENTRY ENGINE AUDIT
--------------------------------------------------------------------------------
- Fundamental Invariant: Sum(Debits) == Sum(Credits).
- Dual-Currency Integrity: Evaluated separately for SDG (tolerance < 1.0) and USD (tolerance < 0.05)
  to accommodate minor floating-point rounding.
- Strongest Enforcement Points:
  1. Client Engine (`validateJournalEntryBalance` in `accountingService.ts` line 395).
  2. UI Modal Guard (`AccountingView.tsx` line 193 blocks submission if unbalanced).
  3. Server API Validation (`server.ts` POST `/api/accounting/validate-entry` lines 127-160).
  4. Automatic JVs: Symmetrically constructed by operational event generators.


5. JOURNAL ENTRY IMMUTABILITY AUDIT
--------------------------------------------------------------------------------
- Immutability Enforcement:
  * `firestore.rules` line 168-172:
    `match /journal_entries/{entryId} { allow update, delete: if false; }`
  * Deletions and edits of posted JVs are rejected by Firestore security rules.
- Compensating Reversals:
  * When an invoice is voided, `generateVoidInvoiceJournalEntry` creates `JV-REV-[number]`
    with exact inverse debit/credit lines.
  * Original JV (`JV-INV-[number]`) remains completely preserved in history.

16. FINANCIAL STATEMENTS AUDIT
--------------------------------------------------------------------------------
- Trial Balance (ميزان المراجعة):
  * Computed in `calculateTrialBalance(accounts, journalEntries)`.
  * Aggregates opening balances and debit/credit movements for every account.
  * Dynamically computes `net_balance_sdg` and `net_balance_usd` based on account nature.
  * Visual balance badge confirms `Total Debits == Total Credits`.
- Income Statement (قائمة الدخل):
  * Computed in `calculateIncomeStatement(journalEntries)`.
  * Formula:
    Sales Revenue (4100)
    - COGS (5100)
    = Gross Profit
    - Operating Expenses (5200-5800)
    = Net Operating Profit
    + Net FX Variance (4200 - 5500)
    = Net Profit (صافي الربح)
- Balance Sheet & Cash Flow:
  * Balance Sheet accounts are visible within the Trial Balance; dedicated standalone
    Balance Sheet and Cash Flow tabs are not yet created.


17. SOURCE DOCUMENT TRACEABILITY
--------------------------------------------------------------------------------
- Traceability Links:
  * Invoice JV: `reference_type: 'invoice'`, `reference_id: invoice.id`, `entry_number: JV-INV-[number]`.
  * Payment JV: `reference_type: 'payment'`, `reference_id: payment.id`, `entry_number: JV-REC-[id]`.
  * Expense JV: `reference_type: 'expense'`, `reference_id: expense.id`, `entry_number: JV-EXP-[id]`.
  * Void JV: `reference_type: 'void'`, `reference_id: invoice.id`, `entry_number: JV-REV-[number]`.
  * Traceability is fully bi-directional and audit-compliant.


18. IDEMPOTENCY OF ACCOUNTING POSTING
--------------------------------------------------------------------------------
- In-Memory & Database Deduplication:
  * JVs use deterministic IDs: `jv-inv-[id]`, `jv-pay-[id]`, `jv-exp-[id]`, `jv-void-[id]`.
  * Writing with `setDoc(doc(db, ..., jvId), jv)` guarantees idempotent writes.
  * Rapid double-clicks or retries overwrite the exact same JV document without duplicating.


19. ATOMICITY & TRANSACTION INTEGRITY
--------------------------------------------------------------------------------
- Split-Write Finding (HIGH RISK):
  * In `createInvoice`, operational changes (invoice, stock, customer debt, counter) are
    executed in a Firestore `runTransaction`. However, the journal entry write:
    `await setDoc(doc(db, 'organizations', orgId, 'journal_entries', invJv.id), invJv);`
    occurs AFTER the transaction block!
  * If a client disconnects immediately following transaction commit, the invoice exists
    without its corresponding journal entry.
  * Recommendation: Include `txn.set(doc(db, ..., 'journal_entries', invJv.id), invJv)`
    INSIDE the `runTransaction` callback.


20. SECURITY / TENANT ISOLATION
--------------------------------------------------------------------------------
- Subcollection Tenant Isolation:
  * Accounts: `/organizations/{orgId}/accounts/{accountId}`
  * Journal Entries: `/organizations/{orgId}/journal_entries/{entryId}`
- Rules Access Matrix:
  * Accounts Read: Any org member (`isOrgMember(orgId)`).
  * Accounts Create/Update: Owner, Admin, Accountant (`hasAnyRole(orgId, ['Owner', 'Admin', 'Accountant'])`).
  * Accounts Delete: Owner or Admin.
  * Journal Entries Read: Owner, Admin, Accountant.
  * Journal Entries Create: Owner, Admin, Accountant, Sales, Cashier (automated POS posting).
  * Journal Entries Update/Delete: STRICTLY FORBIDDEN (`if false`).
- Cross-Tenant Attacks:
  * User in Org A cannot read or write to Org B's accounts or journal entries.


21. CLIENT TRUST BOUNDARY
--------------------------------------------------------------------------------
- Manual Journal Entries:
  * Currently submitted directly from the client via `addJournalEntry`.
  * Express server endpoint (`POST /api/accounting/validate-entry`) validates balance,
    but client Firestore SDK performs the final write.
  * Risk: A malicious authenticated Accountant could forge arbitrary balanced entries.
    Mitigated by strict append-only rules and immutable audit logs.


22. BACKFILL / MIGRATION SAFETY
--------------------------------------------------------------------------------
- Non-Destructive Tenant Migration:
  * Existing users can migrate to `/organizations/{orgId}` without data loss.
  * Default accounts are created idempotently (`merge: true`).
  * Existing invoices and payments retain their operational IDs when JVs are mapped.


23. PRECISION / ROUNDING AUDIT
--------------------------------------------------------------------------------
- Currency Utilities:
  * `safeAdd`, `safeSub`, and `safeMul` in `currency.ts` mitigate IEEE 754 floating-point errors.
  * Decimals configured tenant-wide (`sdg_decimals: 2`, `usd_decimals: 2`).
  * Dual-currency equality checks use bounded tolerances (< 1.0 SDG, < 0.05 USD).


24. ACCOUNTING AUDIT TRAIL

  * Captures user UID, user email, action (`invoice:create`, `payment:record`, `invoice:void`),

  * Rules prohibit modification or deletion of audit logs.


25. PERFORMANCE / SCALE REVIEW
--------------------------------------------------------------------------------
- Query Strategy:
  * `AppContext.tsx` currently fetches all journal entries via `getDocs(collection(...))`
    without pagination.
- Scalability Projection (SIMULATION):
  * 1,000 JVs: ~1.2 MB payload, < 200ms parse time (Acceptable).
  * 10,000 JVs: ~12 MB payload, browser memory pressure during tab switching.
  * 100,000 JVs: Client crash risk without date-range filtering or pagination.
- Recommendation: Introduce date-bounded queries and cursor pagination for GL views.
