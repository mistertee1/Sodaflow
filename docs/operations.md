# تفعيل الإصلاحات

1. خذ نسخة احتياطية من Firestore وStorage في بيئة الإنتاج الحالية، واحفظ إعدادات المشروع والقاعدة المسماة.
2. لا تفعّل هذا الفرع أثناء تعطل وصول الخادم إلى Firestore. افحص `/api/health/ready` ثم شغّل `npm run billing:readiness` من بيئة الاعتماد التي ستجري الترحيل. يجب أن تنجح Firebase وFirestore؛ عدم جاهزية Storage يخص رفع الصور ولا يمنع مزامنة الفواتير.
3. افحص البيانات التاريخية: إصدار الفاتورة مقابل قيدها، ورصيد الذمم مقابل سندات التحصيل، وحركات المخزون مقابل الكمية الحالية. لا تعدّل قيداً تاريخياً لإخفاء فرق.
4. اضبط الاعتمادات الخادمية. `firebase.json` يستهدف قاعدة المشروع الافتراضية `(default)`؛ `firebase.emulator.json` منفصل للاختبارات. يجب أن يطابق مشروع حساب الخدمة مشروع الواجهة (`sodaflow`)، وأن يشمل نطاق متغير الاعتماد Functions في Netlify.
5. شغّل معاينة الترحيل `npm run billing:migrate`؛ إذا ظهرت اشتراكات مدفوعة غير موثقة فأعد توفير مفتاح التحقق السابق أو راجع العقود. لا يغيّر السكربت الباقات غير الموثقة ولا يخفضها تلقائياً. بعد مراجعة النتائج نفّذ `npm run billing:migrate -- --apply`. يحفظ المالك والسجلات والاستخدام التاريخي ويهيئ الباقات المفقودة دون الكتابة فوق تعديلات الإدارة.
6. عيّن UID محدداً لبريد مؤكد تابع لإدارة المنصة عبر `npm run billing:bootstrap -- FIREBASE_UID` للمعاينة ثم أضف `--apply`. لا يحصل أول مسجل أو Owner شركة على صلاحية المنصة تلقائياً.
7. بعد نجاح المراحل السابقة، انشر Rules والفهارس عبر `npm run deploy:firebase:rules` ثم انشر هذا الفرع في نافذة صيانة. القواعد تمنع الكتابات المباشرة، والخادم يفرض الاشتراك والصلاحيات قبل كل عملية محمية. واجهة `main` الحالية لديها fallback إلى API عند رفض الكتابة المباشرة، لكنه يعتمد على نجاح وصول الخادم. لا تنشر القواعد الجديدة قبل إصلاح ذلك الوصول.
8. التحقق التشغيلي المطلوب عند التفعيل: دخول بريد مؤكد، بيع وتحصيل بأدوار Owner وCashier وViewer، إعادة إرسال نفس الطلب دون تكرار، منع مؤسسة أخرى، حدود 100 فاتورة ومقعد الموظف، انتهاء الاشتراك، والفصل بين Company Admin وSuper Admin. لم تُشغّل هذه السيناريوهات آلياً في هذه الجولة، وفق طلب المستخدم.

الـ workflow اليدوي `Deploy Firebase rules` ينفذ الجاهزية ومعاينة الترحيل ثم تطبيقه وتعيين UID اختياري قبل نشر القواعد والفهارس. يشمل تغييرات بيانات تجارية؛ راجع المعاينة من بيئة موثقة أولاً ولا تستعمله أثناء العمل المتزامن دون تنسيق نافذة التفعيل.

## الاشتراكات

إنشاء مؤسسة جديدة يبدأ بخطة Free ودور Owner. Free تسمح بـ100 فاتورة طوال عمر المؤسسة، والمالك مع موظف إضافي واحد. الإبطال أو حذف السجلات التاريخية أو الاستعادة أو تغيير الباقة لا يصفر الاستخدام. الدعوات المعلقة غير المنتهية تحجز مقاعد. التجربة سبعة أيام ومرة واحدة لكل مالك؛ استخدامها في شركة أخرى مملوكة له يمنع بدء تجربة ثانية.

تدار الشركات والباقات والتجديد والتعليق والتمديد والطلبات والسجل الرقابي من `/super-admin`. الوصول يتطلب `superAdmin: true` في token وسجلاً فعالاً بدور `super_admin` في `platformAdmins/{uid}`. يُفحص الشرطان في الخادم وعند المعاملات. مدير الشركة لا يكتب حقول الاشتراك أو الباقات؛ Owner يرسل طلب تغيير فقط، والإدارة تقبله أو ترفضه مع سبب. عمليات الكتابة تتطلب revision الحالية ومعرّف إعادة محاولة، وتسجّل الحدث والقيم القديمة والجديدة داخل نفس المعاملة.

البيانات المركزية: `organizations/{id}` للحالة والباقة وتواريخ الاشتراك وبيانات التجديد، `plans/{id}` للأسعار والمدة والحدود والـ features، `subscriptionEvents/{id}` للسجل غير القابل لتعديل العميل، و`subscriptionRequests/{id}` للطلبات. `billingTrialClaims` و`billingOperations` سجلات خادمية لمنع إعادة التجربة وتكرار العمليات. القيم المعروضة في meta للاستخدام التوافقي لا تمنح الحقوق؛ الخادم يقرأ الباقة المركزية عند تنفيذ العملية. انتهاء الاشتراك يمنع العمليات المحمية دون محو الفواتير والسندات التاريخية. Super Admin لا يرث الوصول إلى التفاصيل المالية داخل الشركات.

أداة الطوارئ تستخدم نفس خدمة الاشتراكات والصلاحيات والسجل، ولا تمنح باقة بمجرد امتلاك ملف اعتماد:

```sh
node --import tsx scripts/set-subscription.ts ADMIN_UID ORG_ID Professional --operation-id UNIQUE_ID --reason 'Manual renewal reference'
```

يتطلب ADMIN_UID حساب Super Admin مؤكداً. `BILLING_SIGNING_SECRET` مطلوب أثناء ترحيل العقود القديمة الموقعة؛ لا تغيّره قبل اكتمال الترحيل. لا توجد بوابة دفع أو Webhook عام مفعل في هذا الفرع. الربط اللاحق يضيف endpoint خادمياً يتحقق من توقيع المزود وحالة الدفع قبل استدعاء الخدمة، ويستخدم event ID من المزود كمرجع فريد، ثم يسجل method وreference والتجديد في metadata. لا تقبل plan أو تاريخاً أو حدث دفع غير موثق من العميل.

حساب تشغيل API يحتاج صلاحيات Firestore للقراءة والمعاملات (`roles/datastore.user`) والوصول إلى Firebase Auth للتحقق من المستخدم والإلغاء. افصل حساب الترحيل وتعيين claims ونشر Rules عن حساب التشغيل؛ تعيين claims يحتاج صلاحية إدارة Firebase Auth ونشر Rules يحتاج صلاحية Firebase Rules المناسبة. لا توسّع حساب التشغيل إلى Owner للمشروع لحل خطأ وصول.

## تدقيق البيانات التاريخية

فحص نسخة محلية لا يحتاج اعتماداً سحابياً:

```sh
node --import tsx scripts/audit-financial-data.ts --backup backup.json > findings.json
```

أو استخدم حساب خدمة بصلاحية قراءة فقط لفحص المؤسسة:

```sh
node --import tsx scripts/audit-financial-data.ts --org ORG_ID > findings.json
```

الفحص يقارن الفواتير والذمم بقيود الإصدار والتحصيل، وأرصدة العملاء بالفواتير، والمخزون بحركاته. يراجع توازن القيود والمراجع المفقودة والتكرار، ويخرج معرّفات ومبالغ دون أسماء العملاء. رمز الخروج 2 يعني وجود نتائج تحتاج مراجعة. لا يكتب أو يعكس أو يصلح أي سجل؛ القيود الافتتاحية أو التسويات القديمة قد تفسر بعض الفروقات، ويجب فحص المستندات الأصلية قبل التصحيح.

## النسخ والاستعادة

تصدير النسخة لا يعتمد صفحات العرض، ولا يستبدل هوية أو عضوية المؤسسة. الاستعادة تتطلب مؤسسة فارغة ونسخة تجتاز فحص الاتساق المالي، وتُبقي المالك والعضويات والاشتراك الحاليين. الحد 350 سجلاً يحافظ على هامش آمن داخل حدود المعاملة؛ الملفات الأكبر تحتاج ترحيلاً مرحلياً مع إبقاء المؤسسة غير نشطة حتى اكتماله. المخزون والقيود الأصلية محفوظة؛ عملية المزامنة تجلب أحدث نسخة ولا تعيد كتابة بيانات محلية فوقها.

## الصور

الرفع يتم عبر الخادم بحجم أقصى 2MiB وأنواع PNG/JPEG/WebP/GIF، مع فحص توقيع الملف وصلاحية رفع شعار أو إيصال. لا يعتمد على قراءة عضوية من قاعدة Firestore أخرى. روابط الصور الحالية وروابط التحميل ذات الرمز تظل روابط قابلة للعرض لمن يملكها، فلا تنشر روابط إيصالات حساسة.

## أخطاء الحفظ

افحص `/api/health/ready` قبل تجربة الحفظ: `firebase_project_mismatch` يعني أن إعداد المشروع أو مفتاح الخدمة يخص مشروعاً آخر، و`firebase_credentials_invalid` يعني أن المفتاح مرفوض، و`firestore_database_missing` يعني أن القاعدة المحددة غير موجودة، و`firestore_access_denied` يعني نقص صلاحية حساب الخدمة. `storage_bucket_missing` أو `storage_access_denied` يخصان حاوية الصور. أصلح الإعداد المحدد ثم أعد النشر؛ حالة `/api/health` وحدها لا تثبت الاتصال بقاعدة البيانات. لا ترسل المفتاح إلى المتصفح أو تضعه في Git.

النجاح يظهر بعد تأكيد Firestore Transaction. فشل الاتصال يترك معرّف الطلب لإعادة المحاولة. لا تضغط إنشاء عملية جديدة لتعويض طلب غير مؤكّد؛ أعد الطلب بالبيانات نفسها. عدّاد revision يُراقب عبر Firestore realtime listener ويعيد تحميل snapshot عند وصول تعديل أحدث. السجلات الرقابية وidempotency تُكتب ضمن نفس المعاملة، وليس بعد نجاحها.

## المزامنة في فرع الاشتراكات

الحفظ والقراءة المحمية يمران عبر API إلى قاعدة Firestore الافتراضية للمشروع `sodaflow`. يحتفظ التطبيق بالكاش المحلي للعرض السريع فقط، بينما Firestore هو مصدر الحقيقة. معاملات المخزون وأرصدة العملاء والعدادات والترقيم وidempotency تتحقق من الباقة الفعلية وتاريخ الانتهاء في الخادم. التقارير المالية المتقدمة تستخدم endpoint محمياً؛ تعطيل الـ feature يمنع الطلب حتى إذا عدّل المستخدم الواجهة.

المتصفح يراقب مستند revision للقراءة فقط، ويعيد المطابقة عند التركيز وعودة الاتصال وكل 30 ثانية. استعادة قائمة الشركات أثناء تعطل API تستخدم قراءة Web SDK مقيدة بهوية المستخدم وقواعد الإنتاج؛ لا تنشئ شركات بديلة ولا تغيّر العضوية أو الاشتراك. هذا المسار لا يعوض غياب صلاحية الخادم للكتابة في وضع الاشتراكات المركزية.

Firestore Transactions تحتاج اتصالاً بالشبكة. عند عدم الاتصال يمكن عرض آخر snapshot مؤكد من الكاش، لكن لا تُعتبر عملية مالية محفوظة قبل تأكيد Firebase.

## تبعيات التشغيل

يتضمن ملف القفل إصدارات مصحّحة من `@grpc/grpc-js` و`uuid` عبر `overrides`، لمعالجة التبعيات القديمة في Firebase وGoogle Cloud مع إبقاء صيغة CommonJS المستخدمة فيها. راجع [تنبيه gRPC الرسمي](https://github.com/grpc/grpc-node/security/advisories/GHSA-m9gg-hp2v-232j) و[تنبيه UUID الرسمي](https://github.com/uuidjs/uuid/security/advisories/GHSA-w5hq-g745-h8pq) عند تحديثها. فحص `npm audit --omit=dev` بتاريخ 2026-10-01 لم يجد تنبيهات، ويعاد في CI؛ النتيجة لا تغني عن اختبارات التوافق عند تحديث الحزم.
